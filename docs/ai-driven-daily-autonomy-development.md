## 1. 文档目的

本文件解决阶段 5—7 验收后暴露出的核心问题：玩家在剧本没有逐字列出行动时，网页不能只剩下“剧本按钮”；同时，AI 不能因为追求自由度而凭空创造关键物品、任务、人物、秘密或主线后果。

本阶段的目标是建立一个受约束的 AI 日常自治层：

- AI 负责理解玩家的自然语言，判断当前情境中可能出现的日常机会，并提出结构化候选；
- Python 规则层负责检查地点、时间、资源、权限、来源、故事影响和 NPC 边界；
- 只有通过校验的候选才能形成确认事件；
- 叙述器只能描述确认事件，不能把候选或想象直接写进世界。

核心原则：

> AI 扩展可玩的可能性，程序限制 AI 不偏离剧本和已确认世界事实。

## 2. 与现有架构的关系

本阶段不替换现有的事件存储、投影、长期记忆、NPC 认知和 Director 的权威原则，但会对当前纵向切片做分阶段的领域拆分。V4.2 Markdown 只作为内容源，运行时只能使用经过结构校验、引用校验和事件编译的目录。

现有能力可以继续复用：

- `DirectorProposal`：扩展为日常候选提议，但仍然不能直接写投影；
- `search_location`：从“静态容器搜索”扩展为“地点机会搜索”；
- `item.transferred`：继续作为所有权转移的唯一权威事件；
- `NpcDecisionContext v2`：增加资源、边界、日程和当前请求情境；
- 长期记忆：只接收确认事件，不接收 AI 候选；
- `world.reported`：继续承载周报/月报，不用于伪造日常物品；
- V4.2 编译目录：增加 Canon 层级、主线状态机、支线协议、地点机会、NPC 卡、日程、事件种子、文书模板和普通物品生成政策。

不可改变的核心原则见：

- `docs/core-principles.md`
- `docs/event-specification.md`
- `docs/domain-model.md`
- `AGENTS.md`

## 3. 当前缺口与必须优化的部分

### 3.1 环境交互过度依赖静态物品容器

当前厨房可以找到食物，是因为厨房配置了真实容器和物品。这个机制保证了来源安全，但不能覆盖街道摊贩、酒馆、临时市场、公共厨房和 NPC 提供的日常机会。

优化方向：

- 不再把“能做什么”表示为地点固定白名单；
- 增加 `WorldAffordance` 地点机会层；
- 机会可以由剧本固定定义，也可以由 AI 在已定义的机会模板中选择；
- AI 不能创建没有来源的建筑、商店、人物或库存；
- 搜索没有结果仍然是正常事件，不是非法行动。

### 3.2 剧本道具和日常物品缺少统一契约

如果剧本道具和 AI 日常物品使用不同结构，后续会出现物品能显示但不能拿取、能拿取但不能使用、能送礼但没有所有权来源等问题。

优化方向：

- 物品定义和物品实例分离；
- 所有物品使用同一套字段、操作和事件；
- 普通物品、情境物品和故事关键道具使用显式重要性等级；
- AI 只能生成普通物品候选，不能直接生成关键道具。

### 3.3 日常行为与主线影响没有明确分级

“和 NPC 吃饭”可以改善关系，但不能自动解决债务；“在街上闲逛”可以发现普通机会，但不能自动发现终局秘密。

优化方向：

- 所有候选带 `narrativeWeight` 和 `storyImpact`；
- 日常回合默认只能产生 `routine` 或受限的 `soft` 结果；
- `story` 和 `major` 结果必须拥有剧本触发条件和明确玩家行动；
- 日常事件不能消耗或推进主要剧情节拍，除非另有确认事件。

### 3.4 NPC 关系容易被错误地简化为总分

好感度只是状态摘要。借钱、隐瞒、提供帮助和参与犯罪必须由 NPC 的知识、资源、人格、风险和当前情境共同决定。

优化方向：

- 保留 `favor / trust / respect / fear / suspicion / debt` 多维关系；
- 禁止使用单一总分直接映射行为；
- AI 提出 NPC 反应，程序验证 NPC 是否知道、是否有资源、是否违反硬边界；
- 关系变化必须绑定可观察的确认事件。

### 3.5 代码改造规模必须显式管理

现有代码是阶段 1—7 的可运行纵向切片，不是最终领域架构。`engine.py`、`scenario.py`、`projection.py`、`npc_decision.py` 和 `game-client.tsx` 同时承担多个职责，无法安全地继续堆叠条件分支。因此阶段 7.5 不采用一次性重写，而是采用“新模块先并行、旧入口做兼容路由、逐领域切流、最后删除旧分支”的迁移方式。

每个重构阶段必须完成四个门槛：

1. 旧事件和旧存档仍能重放，且关键投影摘要一致；
2. 新模块有纯 Python 契约测试，成功、前置条件失败、无结果和重复提交至少各有用例；
3. 旧入口只负责适配，不再新增领域规则；
4. 通过网页玩家验收后才允许删除旧实现。

预计会修改的代码边界：

| 领域 | 主要现有文件 | 迁移后的模块 |
|---|---|---|
| 剧本编译 | `scenario.py`、已退役的 V3 编译入口 | `v4_compiler.py`、V4.2 引用与校验器 |
| 行动解析 | `engine.py`、`intent.py` | `action/normalizer.py`、`action/intent_router.py` |
| 地点机会 | `engine.py`、`director.py` | `affordances/`、`routine/` |
| 物品与背包 | `engine.py`、`projection.py` | `inventory/`、`commerce/` |
| NPC 决策 | `npc_decision.py` | `npc_policy/`、`social/` |
| 世界自治 | `director.py` | `world_simulation/`、`economy/` |
| 事件投影 | `projection.py` | `event_handlers/` 注册式投影器 |
| 玩家网页 | `game-client.tsx` | `WorldMap`、`SceneView`、`InventoryPanel`、`ActionComposer` |

旧模块在迁移期保留公开接口和事件版本适配器；禁止为了“快速切换”删除历史事件、把 AI 输出直接写入投影，或让前端复制规则。

### 3.6 本轮新增的设计冻结项

以下要求从本轮开始成为开发和验收的硬约束，不再作为“以后再考虑”的体验建议：

1. **开放式日常行为**：地点不提供动作白名单。玩家在街道找食物、找临时工作、吃饭、散步、打扫、发呆或等待，只要符合地点、时间和资源边界，就必须进入正常的行动判定；找不到结果是合法结果，不得被误报为“没有新的可用通路”。
2. **日常与主线分层**：日常事件可以影响时间、普通物品、小额金钱、熟悉度、人情和短期印象，但不能仅凭一次日常行动完成主线、创建关键道具、改变终局或写入重大法律后果。
3. **统一物品契约**：剧本道具、商店物品和 AI 生成的普通物品都必须使用 `ItemDefinition` + `ItemInstance`，明确来源事件、容器、所有者、数量、状态、过期时间和标准操作。任何叙述中出现的物品，如果没有实例化事件，就不属于世界。
4. **日常物品的可复用性**：普通物品可以在剧本声明“通用材料/普通礼物/普通食物”时参与支线或主线的非唯一条件；是否绑定故事由独立的 `story.item_bound` 事件决定，AI 不能自行把普通物品升级为关键道具。
5. **NPC 主观性**：关系数值只表示历史摘要，不能直接映射“好感达到多少就借钱”。NPC 必须综合自身知识、错误信念、资源、职责、人格、日程、风险、法律底线和关系来源，由 AI 提出反应候选，程序检查硬约束并记录原因来源。
6. **零推进日**：没有固定建议篇幅、章节次数或每日剧情产出。玩家可以用一天挣钱、失败、休息、陪伴、家务或发呆；世界按日/周/月时间尺度自然结算，AI 不得为了“让回合有内容”强行添加线索或剧情。
7. **大幅重构承认**：阶段 7.5 的完成标准不是“旧文件增加几个分支”，而是完成权威内核、环境机会、物品、NPC、世界自治和网页职责的逐领域迁移。旧实现只有在新旧回放摘要、真实玩家验收和回归集全部通过后才允许退役。

## 4. 权威数据流

```text
玩家自然语言
    ↓
意图解析与结果性声明清洗
    ↓
公开状态、地点机会、NPC 日程、物品和时间上下文
    ↓
AI 提出日常候选或 NPC 反应候选
    ↓
结构校验
    ↓
地点/时间/权限/资源/故事影响验证
    ↓
NPC 主观决策验证
    ↓
Confirmed Result
    ↓
原子事件提交
    ↓
状态投影、记忆写入、认知传播
    ↓
AI 根据确认结果生成叙述
```

低层级内容不能覆盖高层级事实：

1. 确认事件；
2. 当前状态投影；
3. NPC 自己的知识、信念和关系历史；
4. 玩家和 NPC 的发言；
5. AI 候选和叙述。

## 5. 地点机会模型 `WorldAffordance`

地点机会表示“在这个地点、这个时间、以这个身份，玩家可能合理尝试什么”。它不是确认事实，也不是前端按钮，而是供解析器、日常 Director 和验证器使用的结构化输入。

### 5.1 必要字段

| 字段 | 说明 |
|---|---|
| `affordanceId` | 稳定 ID |
| `locationId` | 所属地点 |
| `kind` | `search / commerce / meal / social / work / rest / observe / travel` |
| `title` | 开发者和 AI 使用的短标题 |
| `publicDescription` | 玩家可见描述，可为空 |
| `schedule` | 营业或可用时间规则 |
| `participants` | 可能参与的 NPC 或组织 |
| `resourceTemplates` | 可提供的普通物品模板 |
| `prerequisites` | 钱、权限、天气、日程、关系或地点条件 |
| `outcomeTemplates` | 找到、售罄、拒绝、部分成功、无结果等候选 |
| `storyImpact` | `none / soft / story / major` |
| `visibility` | `public / player / gm` |
| `sourceEntryId` | V4.2 原稿或剧本包来源 |
| `validFrom / validUntil` | 生效时间范围 |
| `maxDailyUses` | 日常资源或机会的次数限制 |

### 5.2 地点搜索规则

玩家输入“我去街上找点吃的”时：

- 解析为环境资源搜索；
- 查询当前地点及其公开可访问的机会；
- 按世界时间、营业状态、天气、库存、价格和玩家能力筛选；
- AI 可以在候选模板中选择叙述和合理结果；
- 程序确认实际物品、货币和时间变化；
- 找不到结果也提交 `search.performed` 和时间事件；
- 找到物品不等于自动拥有，购买或取用必须另一个权威事件。

### 5.3 街道找食物示例

可能结果：

- 找到仍在营业的廉价面包摊；
- 找到一家酒馆，但当前价格超出玩家预算；
- 摊贩已经卖空，只留下气味和位置线索；
- 因为暴雨，街边摊已收摊；
- 发现公共厨房，但需要排队；
- 没有找到合适食物。

AI 不能直接创造一个没有剧本来源的永久商店。如果需要一个新摊贩成为长期可访问地点，必须经过剧本包或开发者工具正式编译。

## 6. 统一物品模型

### 6.1 定义与实例分离

`ItemDefinition` 描述一类物品，`ItemInstance` 描述世界中的具体数量或单件。

### 6.2 物品定义字段

| 字段 | 说明 |
|---|---|
| `itemDefinitionId` | 物品类型稳定 ID |
| `name / aliases` | 名称和解析别名 |
| `category` | `food / drink / tool / document / clothing / currency / gift / evidence` 等 |
| `tags` | 可食用、可赠送、可组合、可装备、可作为材料等 |
| `stackable` | 是否可堆叠 |
| `weight / volume` | 背包容量计算 |
| `baseValue` | 基础价值，不等于当前售价 |
| `conditionModel` | 完好、破损、腐坏、过期等 |
| `uses` | 可执行的标准操作 |
| `legalStatus` | 普通、受限、非法、证据 |
| `criticality` | `mundane / contextual / story_bound / major_key` |
| `storyBindingPolicy` | 是否允许绑定到故事事件 |
| `visibilityPolicy` | 公开、持有者可见、GM 私密 |

### 6.3 物品实例字段

| 字段 | 说明 |
|---|---|
| `itemInstanceId` | 世界中的唯一实例 ID |
| `itemDefinitionId` | 对应物品定义 |
| `quantity` | 数量 |
| `containerId` | 当前容器 |
| `ownerCharacterId` | 当前所有者，可为空 |
| `condition` | 当前状态 |
| `expiresAt` | 过期时间，可为空 |
| `discoveredAt` | 被发现时间 |
| `sourceEventId` | 创建或获得来源 |
| `lastChangedEventId` | 最近变化来源 |
| `storyBindingEventId` | 被故事正式绑定的事件，可为空 |
| `customProperties` | 仅允许模板声明的扩展字段 |

### 6.4 标准物品操作

所有物品都必须通过统一操作检查：

- `inspect`：查看公开或已知信息；
- `take`：从地点或容器取用；
- `transfer`：给予、交易或转移所有权；
- `consume`：食用、饮用或消耗；
- `use`：作为工具、材料或证据使用；
- `equip`：装备；
- `combine`：与其他物品组合；
- `discard`：丢弃；
- `destroy`：销毁；
- `expire`：由时间系统过期。

AI 只能提出操作候选。程序必须校验所有权、位置、数量、状态、权限和操作标签。

## 7. 日常 AI 生成物品的故事边界

### 7.1 默认分类

AI 日常生成物品默认只能是 `mundane`：

- 可以维持饱食度；
- 可以作为普通礼物；
- 可以作为通用低风险材料；
- 可以影响小额交易或短期便利；
- 不能单独解锁主线或终局；
- 不能成为唯一关键证据；
- 不能创建新的长期 NPC、组织或地点。

### 7.2 情境物品

剧本可以声明某类物品拥有通用用途。例如“任意绳索”“任意可书写材料”“任意普通食物”。此时日常物品可以满足非唯一的情境条件，但必须：

- 物品确实存在；
- 标签符合需求；
- 玩家拥有或能访问它；
- 使用事件保留来源；
- 不绕过剧本要求的关键事实。

### 7.3 故事绑定

如果一个日常物品后来确实适合进入支线或主线，必须通过明确的 `story.item_bound` 事件绑定。

绑定要求：

- 剧本或开发者规则声明允许绑定；
- 绑定条件由 Python 校验；
- 绑定前后保留原始创建和获得来源；
- AI 不能自行把 `mundane` 提升为 `major_key`；
- 绑定事件必须可回放、可撤销或明确不可逆。

## 8. 日常事件影响等级

### 8.1 `routine`

只改变短期生活状态：

- 时间；
- 食物或普通物品；
- 金钱的小额收支；
- 当前地点观察；
- 普通社交记录；
- 未来阶段 8 的精力、饱腹度和睡眠。

### 8.2 `soft`

可以造成小幅、可解释的软影响：

- 轻微熟悉度或人情变化；
- 一次性折扣；
- NPC 对玩家的短期印象；
- 普通小道消息；
- 下一次交互的情境修正。

软影响不能自动改变主线阶段、通缉状态、核心任务或关键关系承诺。

### 8.3 `story` 与 `major`

必须拥有：

- 明确剧本来源；
- 触发条件；
- 玩家明确行动或世界自治时间点；
- 因果来源；
- 单回合节拍预算；
- 可回放事件链。

日常 AI 默认不能直接产生这两类结果。

## 9. NPC 决策与关系系统

### 9.1 关系维度不是行为阈值

继续使用多维关系：

- `favor`：人情和即时倾向；
- `trust`：相信主角陈述和承诺的程度；
- `respect`：对能力、边界和可靠性的评价；
- `fear`：威胁或风险压力；
- `suspicion`：怀疑和警戒；
- `debt`：双方可追溯的债务。

这些值是 NPC 历史的投影，不是“超过 50 就同意”的规则。

### 9.2 NPC 决策输入

每次 NPC 决策必须只读取该 NPC 可拥有的上下文：

- 当前知道、相信、怀疑和否认的命题；
- 与玩家的历史事件；
- 当前地点和在场人物；
- 当前时间与日程；
- 自身金钱、物品、职责和组织压力；
- 动机、恐惧、风险偏好和硬拒绝；
- 玩家当前请求的成本、风险和可逆性；
- 可能造成的声誉、法律和关系后果。

### 9.3 NPC 输出选项

AI 只能从结构化选项中选择或提出候选：

- `accept`：接受；
- `decline`：拒绝；
- `partial`：部分满足；
- `conditional`：提出抵押、回报或额外条件；
- `defer`：改天处理；
- `redirect`：提供合法替代方案；
- `conceal`：隐瞒自己知道的一部分，但必须留下来源事件。

### 9.4 借钱示例

玩家说：“玛莎，我一个人吃饭，能不能借我一点钱？”

AI 可以考虑好感和人情，但还必须检查：

- 玛莎当前是否有钱；
- 玩家过去是否履行过承诺；
- 借钱是否会影响白鹭屋经营；
- 玛莎是否相信玩家会偿还；
- 当前是否有其他人在场；
- 请求是否符合玛莎的动机和风险边界。

因此可能得到“借少量钱”“要求记账”“只提供一顿饭”“拒绝但提供工作”或“暂时不方便”等结果。

### 9.5 关系变化写入规则

关系变化必须：

- 绑定可观察事件；
- 区分即时情绪和长期信任；
- 不能由 AI 一次性大幅修改；
- 不能因为同一件日常小事重复叠加；
- 保存 NPC 的决策理由类别和来源，而不是只保存一个数值。

## 10. AI 与程序的责任划分

| 能力 | AI 负责 | 程序负责 |
|---|---|---|
| 意图理解 | 从自然语言识别行动目的 | 防止非法目标和结果性声明越权 |
| 日常机会 | 从已定义机会模板提出合理候选 | 校验地点、时间、日程、库存和来源 |
| 普通物品 | 提出名称、描述和用途候选 | 生成实例、所有权、数量和操作权限 |
| NPC 反应 | 根据人格和认知提出反应 | 检查知识、资源、硬拒绝和关系变化范围 |
| 故事影响 | 识别可能相关但不能自行升级 | 判断是否有剧本触发条件和事件权限 |
| 叙述 | 描写已确认结果 | 禁止新增事实、秘密、物品和任务 |
| 记忆 | 提出可能相关的历史候选 | 只有确认事件才能写入长期记忆 |

## 11. 安全验证器

每个日常候选都必须经过以下检查：

### 11.1 地点检查

- 玩家是否在该地点；
- 机会是否对该地点公开；
- 是否需要先移动或发现；
- 是否把远处 NPC 的位置泄露给玩家。

### 11.2 时间检查

- 商店、摊贩和 NPC 是否在营业或可见时段；
- 是否跨越日、周、月边界；
- 是否超过日常行动时间预算；
- 是否跳过了玩家没有选择的下一步。

### 11.3 资源检查

- 食物、货币、工具和材料是否真实存在；
- 数量、重量、所有权和容器是否一致；
- 交易、食用和赠送是否原子提交；
- 不得凭空获得或重复消耗。

### 11.4 故事边界检查

- `routine` 和 `soft` 不得直接完成主线；
- 日常物品不得自动变成关键道具；
- AI 不得创建没有来源的任务、地点、组织或 NPC；
- 重大后果必须具备剧本条件和来源链。

### 11.5 NPC 认知检查

- NPC 只能使用自己的知识、信念和怀疑；
- 不得读取 GM 私密事实；
- 不同 NPC 可以得到不同结果；
- 错误传闻不能被写入世界事实。

## 12. 事件与存储要求

建议增加或统一以下事件类型：

- `affordance.observed`：玩家观察到可用机会；
- `search.performed`：完成环境搜索；
- `routine.action_performed`：日常行动完成；
- `commerce.offer_found`：发现交易机会；
- `commerce.completed`：交易完成；
- `meal.shared`：共同用餐完成；
- `item.created`：物品实例创建；
- `item.consumed`：物品消耗；
- `item.used`：物品被使用；
- `story.item_bound`：物品被正式绑定到故事；
- `npc.decision_recorded`：保存 NPC 决策选项、来源和结果；
- `relationship.changed`：关系维度发生可追溯变化。

所有新增事件都必须：

- 指定 `schemaVersion`；
- 保存 `sourceEventId` 或等价来源；
- 能被 SQLite 重放；
- 能被 PostgreSQL 迁移；
- 通过幂等键防止重复提交；
- 在普通玩家响应中只暴露受控结果。

## 13. 代码改造判断

这不是在现有搜索逻辑上增加几个条件，而是一次受控的领域拆分。现有事件存储、投影、幂等、长期记忆、认知来源链和叙述边界继续保留；需要重构的是目前集中在少数大文件中的解析、物品、环境和 NPC 判定职责。

当前主要集中点：

- `engine.py` 同时承担输入分流、环境搜索、物品操作、等待、NPC 交互和复合行动，已经超过 2000 行；
- `scenario.py` 同时承担所有剧本 Schema、校验、编译和引用处理；
- `projection.py` 通过大型事件分支更新所有领域状态；
- `npc_decision.py` 同时承担上下文组装、模型请求、结构解析和结果验证；
- `game-client.tsx` 同时承担地图、背包、叙述、操作输入和开发追踪展示。

### 13.1 保留的基础设施

- 追加式事件日志；
- 命令幂等和乐观版本检查；
- SQLite 测试实现与 PostgreSQL 接口；
- 事件重放和状态投影原则；
- 长期记忆的来源、作用域和检索追踪；
- NPC 认知与法律后果链；
- Narrative Plan 和叙述输出验证；
- V4.2 源文件指纹和编译边界。

### 13.2 需要拆分的后端职责

建议逐步建立以下领域模块，旧入口在迁移期只做路由和兼容：

| 新职责 | 从现有位置迁出 | 目标责任 |
|---|---|---|
| `affordances` | `engine.py`、`scenario.py` | 地点机会、可用条件、候选上下文和来源校验 |
| `routine` | `engine.py`、`director.py` | 日常行动候选、影响等级和结果验证 |
| `inventory` | `engine.py`、`projection.py` | 物品定义、实例、容器、所有权和生命周期 |
| `commerce` | 新增 | 报价、库存、货币转移、购买和售罄结果 |
| `social` | `engine.py`、`npc_decision.py` | 用餐、赠礼、借贷、陪伴和轻量关系后果 |
| `npc_policy` | `npc_decision.py` | NPC 资源、认知、人格、硬拒绝和候选验证 |
| `world_simulation` | `director.py` | 日/周/月自治、库存刷新、价格和组织计划 |
| `event_handlers` | `projection.py` | 按领域注册事件投影器，保留统一重放入口 |
| `scenario_compiler` | `scenario.py`、已退役的 V3 编译入口 | 内容 Schema、引用校验、V4.2 编译和版本迁移 |

这只是职责边界，不要求一次移动所有文件。每次拆分必须先保持旧测试通过，再把一个领域迁移到新模块，禁止“大爆炸式重写”。

### 13.3 需要拆分的网页职责

建议将现有玩家页面逐步拆为：

- `WorldMap`：地图层级、可达地点和当前位置；
- `SceneView`：确认叙述、在场人物和环境机会；
- `InventoryPanel`：物品、数量、状态、容量和操作；
- `ActionComposer`：自由输入和结构化快捷操作；
- `RoutineOutcome`：无结果、部分成功、售罄、买不起和条件不足；
- `RelationshipView`：只展示玩家可合理感知的关系历史，不显示 NPC 私密数值；
- `DeveloperTrace`：只在开发模式显示候选、验证和拒绝原因。

前端只能提交命令和展示后端公开状态，不能自行判断库存、价格、能否食用、NPC 是否愿意或物品能否推动任务。

### 13.4 兼容与迁移策略

- 现有存档必须继续重放；
- 旧 `item.created`、`item.transferred` 和容器事件通过版本适配器进入新模型；
- 新事件必须显式声明 `schemaVersion`；
- 旧剧本物品缺少的字段由迁移默认值补齐，但关键性不能由 AI 推断；
- 每次剧本结构变化更新 `scenarioVersion` 和内容指纹；
- 新旧投影在迁移测试中比较物品数量、位置、关系、时间、知识和时钟摘要；
- 不允许通过删除旧事件来“修复”新模型；
- 不要求一次完成 PostgreSQL 上线，但 SQLite 和 PostgreSQL Schema 必须同步设计。

## 14. AI 驱动而非模板白名单

地点机会不是“这个地点只能执行这些动作”的按钮清单。它描述的是 AI 生成内容时不能越过的边界：地点类型、社会环境、时间、资源类别、价格范围、可能参与者和故事影响上限。

### 14.1 AI 可以动态生成的内容

在机会策略允许时，AI 可以提出：

- 临时摊位、普通顾客、路人和短时服务人员；
- 普通食物、饮品、生活用品和低价值礼物；
- 售罄、排队、涨价、关门、天气影响和误会；
- 普通工作、休息、用餐、闲聊、陪伴和小额交易；
- 对环境细节的非关键描写。

这些内容仍需生成唯一 ID、来源事件、生命周期和可见范围。临时内容默认不能成为永久地点、核心 NPC、组织成员、任务发布者或关键证据。

### 14.2 AI 不可动态生成的内容

- 主线或重要支线任务；
- 关键道具和唯一证据；
- 会改变组织终局的永久 NPC；
- 新城区、永久建筑或重要组织；
- 隐藏事实的真实答案；
- 通缉、死亡、重大债务和不可逆关系承诺；
- 直接绕过剧本硬期限、条件或唯一身份要求的解决方案。

### 14.3 临时内容晋升

重复出现的普通摊贩、路人或物品可以获得持续性，但不能由叙述器自行晋升：

1. 已有确认创建事件；
2. 玩家与其发生了多次确认互动；
3. 剧本生成策略允许该类别持久化；
4. 程序提交 `entity.promoted` 或 `story.item_bound`；
5. 晋升后仍不能自动获得主线权限。

这使 AI 能创造有连续性的日常生活，同时避免一段即兴叙述改写剧本骨架。

## 15. 分阶段开发顺序

以下阶段必须依次进行。用户提供最终剧本后，先完成 7.5A 的内容审计和约束编译，再开始代码实现。

### 15.1 每个子阶段的固定开发流程

每个子阶段都必须留下四类可审计产物，不能只提交代码：

1. **设计产物**：领域模型、事件 Schema、来源边界、失败与降级路径、与 V4.2 的引用关系，以及明确不属于本阶段的内容。
2. **实现产物**：新的纯领域模块、兼容适配器、API 公开状态和迁移脚本。旧入口只能路由到新模块，不得在旧入口继续增加规则分支。
3. **自动验证产物**：成功、前置条件失败、无结果、部分成功、重复提交、模型不可用、越权候选、事件重放和旧存档摘要对比测试。
4. **玩家验收产物**：以网页真实玩家身份完成至少一条完整流程，并记录输入、确认结果、时间、物品、关系、可见叙述和是否泄露内部信息。

只有四类产物都完成，且新旧投影摘要一致，阶段才可以标记为“完成”。发现问题时先增加回归用例，再修改规则或内容策略，最后重新进行网页验收。

### 7.5A：V4.2 内容编译与架构边界（已完成）

目标：把剧本从“剧情文本”整理为 AI 可使用的约束、来源和生成策略。

开发内容：

- 审计 V4.2 剧本中的 Canon 层级、地点、建筑、人物、组织、任务、物品、时间线、法律和经济事实；
- 区分硬事实、软设定、生成策略和仅供叙述参考的风格文本；
- 定义 `WorldAffordance`、`GenerationPolicy`、`RoutineEventProposal` 和物品标准格式；
- 为七城区及其建筑声明允许生成的资源类别、临时实体类别、价格范围、营业规律和影响上限；
- 为所有剧本道具补齐 `criticality` 和 `storyBindingPolicy`；
- 定义跨文件引用、来源行号、内容指纹和版本迁移；
- 编写 ADR，确认 AI 生成内容与剧本事实的边界。

代码影响：新增 `v4_compiler.py` 和 V4.2 结构化目录，重构 `scenario.py` 的内容绑定职责并退役已无源文件的 V3 编译入口；本阶段不改变回合结果逻辑，只切换内容加载边界。

验收：编译器可以报告缺失来源、重复 ID、非法关键性、未定义地点机会、跨层引用和越权生成策略；G 层模板不会被写入 C1 世界事实；旧剧本包仍能通过兼容层加载。

### 7.5B：权威内核拆分与迁移门（首个切片完成）

目标：把现有“大引擎”改造成只负责协调的薄入口，为后续 AI 日常和物品生命周期提供稳定的领域接口。

开发内容：

- 定义统一 `EventStore`、`CommandResolver`、`ProjectionRunner` 和 `NarrativeResult` 接口；
- 将输入清洗、意图路由、行动解析、结果验证、事件提交和叙述生成拆成可替换端口；
- 把 `projection.py` 的事件分支迁移为按领域注册的投影处理器，保留旧 `schemaVersion` 适配器；
- 为 `engine.py` 建立兼容外观，旧 API 先转发到新模块，禁止在兼容层新增规则；
- 建立旧存档回放快照，比较时间、位置、物品、关系、认知、任务和世界时钟摘要；
- 增加失败隔离：AI 超时、结构错误或候选越权时只能返回安全结果，不能留下半提交事件。

代码影响：这是阶段 7.5 中最大的基础重构，涉及 `engine.py`、`projection.py`、`scenario.py`、`service.py`、事件 Schema 和 API 响应，但不一次性改写所有业务。先迁移一个事件族并保持全套旧测试通过，再扩大切流范围。

验收：新旧入口对同一命令产生相同确认事件；旧存档可重放；重复提交、版本冲突和模型不可用均不产生部分状态；任何领域规则都能在新模块中独立测试。

### 7.5C：环境机会与日常行动（首个切片完成）

目标：将日常行动从 `engine.py` 的关键词和静态容器分支中拆出，建立独立环境领域。

开发内容：

- 保留 `engine.py` 为命令路由和事务前的纯协调入口；
- 建立环境行动、地点机会筛选和日常结果验证模块；
- 统一搜索、观察、休息、工作、用餐和购物意图；
- 区分“行动不允许”“行动失败”“没有找到”“暂时不可用”和“需要下一步确认”；
- 支持 AI 根据开放式输入选择合理机会，而不是要求剧本逐字列出行动；
- 模型不可用时使用保守的结构化降级，不污染状态。

代码影响：从迁移后的协调入口拆出 `affordances/`、`routine/` 和环境结果验证器，并为新事件增加注册式投影处理器。

验收：同一句“找吃的”在厨房、街道、关门酒馆和无商业区得到不同且有来源的结果；未知合理行为不再默认变成发言或隐藏通道调查。

### 7.5D：统一物品、背包与交易生命周期（首个交易切片完成，迁移中）

目标：让剧本道具和日常生成物品使用同一个权威模型。

开发内容：

- 完成 `ItemDefinition` 与 `ItemInstance` 分离；
- 统一容器、数量、堆叠、重量、体积、所有者、状态、过期和来源；
- 实现检查、取用、购买、转移、赠送、消费、使用、组合、损坏、过期、丢弃和销毁；
- 实现货币、报价、库存和交易的原子事件；
- 实现 `mundane / contextual / story_bound / major_key` 保护；
- 实现普通物品故事绑定，不允许 AI 自行升级关键性。

代码影响：从 `engine.py` 和 `projection.py` 迁出物品规则；更新 `domain.py`、事件 Schema、SQLite/PostgreSQL 表与剧本 `items.json`。

验收：任何物品都能回答“是什么、在哪里、属于谁、从哪里来、能做什么、是否过期、能否进入故事”；重复提交不会复制或重复消费物品。

### 7.5E：受约束的 AI 日常导演

目标：让 AI 成为日常玩法的主要理解和候选生成层，而不是只做叙述润色。

开发内容：

- 为模型构造只含玩家可见事实的 `RoutineContext`；
- AI 输出结构化候选、替代结果、置信度和所依赖的机会 ID；
- 程序验证地点、时间、日程、资源、预算、来源和故事影响；
- 增加 `routine / soft / story / major` 防火墙；
- 支持临时普通实体和普通物品候选，但要求实例化事件与生命周期；
- 支持成功、部分成功、无结果、资源不足、延期、售罄和拒绝；
- 日常行为不自动占用或推进主要剧情节拍。

代码影响：新增日常模型适配与审计记录；扩展 `service.py` 的候选—验证—事件协调，但不允许模型接触数据库写入。

验收：街上找食物、找临时工作、买普通用品、与路人闲聊、独自吃饭、散步和发呆均能得到情境化结果；越权候选全部被拒绝或降级。

### 7.5F：NPC 主观决策与社会关系

目标：让 NPC 由自身认知、人格和利益做决定，关系数值只作为历史摘要。

开发内容：

- 将 NPC 的可支配金钱、物品、职责、日程和组织压力加入上下文；
- 分离熟悉度、即时心情、人情、信任、尊重、恐惧、怀疑和债务；
- 支持共同用餐、陪伴、赠礼、借贷、请求帮助、拒绝、延期和条件交换；
- 限制重复刷礼、重复吃饭和低成本行动的关系收益；
- AI 提出 `accept / decline / partial / conditional / defer / redirect / conceal`；
- 程序检查 NPC 是否知道、是否有资源、是否违反硬拒绝和法律边界；
- 保存决策审计和关系变化来源。

代码影响：拆分 `npc_decision.py`，扩展 `consequences.py`、长期记忆选择和 NPC 认知上下文。

验收：高好感但没钱的 NPC 会拒绝借钱；高信任仍不会违反职业底线；低好感 NPC 在抵押充分时可能有限合作；一起吃饭只产生有限社会影响，不自动披露任务秘密。

### 7.5G：世界自治、经济和日常循环

目标：让日常机会不是每回合临时幻觉，而是统一世界时间中的可持续系统。

开发内容：

- 商铺和摊贩营业、库存消耗与补充；
- 普通物价范围、天气和组织事件造成的价格变化；
- 工作机会、报酬、失败、欠薪和无收入结果；
- NPC 日程、休息、缺席和临时事件；
- 玩家等待、睡觉或离开时的日/周/月结算；
- 临时实体的过期、再次出现和受控晋升；
- 世界变化通过可观察痕迹呈现，不自动向玩家泄露后台事实。

代码影响：扩展 `director.py` 为独立世界模拟模块，增加经济/库存投影和定时事件；复用阶段 6 的延迟传播机制。

验收：玩家一个月不推动主线，城市仍有合理变化；库存与价格不会每次询问随机重置；日常经济不会无限生成金钱或物品。

### 7.5H：玩家网页、地图和背包交互

目标：让网页真正用于游玩，而不是展示开发追踪。

开发内容：

- 地图展示当前地点、可达区域、公开设施和当前可感知机会；
- 背包展示数量、状态、容量、用途、是否可食用/赠送/使用和公开来源摘要；
- 物品支持点击检查、使用、消费、赠送、丢弃和交易；
- 自由输入仍是主要入口，快捷操作只减少重复输入；
- 清楚区分无结果、失败、买不起、关门、售罄、NPC 拒绝和需要下一步确认；
- 玩家模式隐藏候选、内部数值、NPC 私密理由和 GM 事实；
- 开发模式保留候选与验证追踪。

代码影响：拆分 `game-client.tsx`，扩展公开状态 API，但所有最终判定仍留在 Python 后端。

验收：桌面和移动端均能完成寻找食物、购买、放入背包、食用、赠礼和查看结果；UI 不会因动态物品名称、数量或地点机会发生重叠。

### 7.5I：评估、迁移与真实玩家验收

目标：证明自由度提高没有破坏剧本、物品和 NPC 边界。

自动评估至少包含：

- 80 个地点与开放式日常行为案例；
- 60 个物品生命周期、交易、消费和故事绑定案例；
- 60 个 NPC 用餐、借贷、赠礼、拒绝和条件帮助案例；
- 40 个 AI 越权创建人物、地点、任务、秘密或关键道具案例；
- 30 个世界自治、库存、价格和临时实体生命周期案例；
- 30 个重复提交、断线重试、版本冲突和事件重放案例；
- 20 个旧存档和旧剧本包迁移案例。

真实玩家验收覆盖不同地点、昼夜、天气、财富、关系、NPC 日程和模型失败模式。每个失败样本先进入回归集，再修改规则或剧本生成策略。

验收：达到第 16 节指标，旧存档摘要一致，SQLite/PostgreSQL 契约一致，网页玩家模式没有开发信息泄漏。

## 16. 评估指标

阶段 7.5I 完成前必须达到：

- 合理日常请求误拒绝率低于 5%；
- 日常候选无来源物品率为 0；
- 日常候选无来源 NPC/地点/任务率为 0；
- 日常行动误推进主要剧情率为 0；
- 普通物品未经绑定成为关键道具率为 0；
- NPC 私密知识泄漏率为 0；
- 物品重复复制或所有权冲突率为 0；
- 重复提交造成重复消耗率为 0；
- NPC 决策可以追溯到知识、关系、资源、边界和请求事件；
- 玩家能够看懂成功、失败、无结果和条件不足的差别。

## 17. Definition of Done

阶段 7.5I 只有同时满足以下条件才算完成：

- 设计文档、ADR 和路线图已同步；
- 地点机会和物品定义经过结构校验；
- AI 只产生结构化候选；
- 程序验证所有状态变化；
- 所有物品拥有来源、容器、所有者和操作权限；
- 日常行为不能直接推进主线；
- NPC 决策不能退化为单一好感阈值；
- 成功、失败、无结果、部分成功和重复提交都有测试；
- SQLite 重放和 PostgreSQL 迁移协议保持一致；
- 玩家网页完成桌面和移动断点验收；
- 普通玩家看不到 GM 事实和 AI 私密推理；
- 全套后端、前端、API 和真实网页验收通过。

## 18. 与阶段 8 的边界

阶段 7.5 只建立日常事件、物品和 NPC 决策基础，不提前假装已经拥有完整生存规则。

阶段 8 再实现：

- 饱腹度、精力、睡眠和恢复；
- 食物营养、腐坏和消费效果；
- 技能、骰子、战斗和伤病；
- 完整工作收入与经济规则；
- 任务状态机和成长奖励。

阶段 7.5 产生的物品和事件必须为阶段 8 预留标准字段，但不能使用未实现的属性制造假效果。

## 18.1 当前切片验收记录（2026-08-21）

本轮真实玩家验收把“合理日常行为不能被机械拒绝”落实为回归边界：

- 地图点击移动必须提交目标地点的自然语言行动，并在 V4.2 服务上验证当前位置、时间和可达出口；前端不得连接旧端口或旧剧本存档。
- `我想找一些食物`、`厨房里有没有能吃的` 统一进入环境资源搜索；同场 NPC 不能因为“有没有”而抢走意图。
- 搜索结果只报告当前容器中的真实物品；找到物品不自动进入背包，必须再提交取用事件；取用后才能消费。
- 重复搜索仍是正常回合，可以报告仍在原处的物品或没有新结果；不能改写成隐藏通路失败或无关发言。
- `我想拿厨房里的食物` 等明确取用动作优先于资源搜索；目标不明确时返回未解析，不凭空创建物品。
- 前端状态归一化按地点 ID 合并迁移/热更新重复记录，场景出口使用稳定的复合键，避免 React key 冲突遮蔽真实玩家结果。
- 移动端 390×844 断点已检查地图、输入和叙述，没有重叠；玩家模式不显示候选审计和 NPC 私密理由。

## 19. 研究依据

设计参考以下方向，但不允许论文中的生成式机制越过本项目的事件权威边界：

- Generative Agents：日程、环境连续性与经历流；
- LongMemEval：事实回忆、时间更新、拒答和长期一致性；
- Memory-Driven Role-Playing：Anchoring、Selecting、Bounding、Enacting；
- A-MEM：记忆之间的显式链接和动态组织；
- THEANINE：旧事实保留、时间关联和记忆更新；
- RMM：不同粒度的场景和事件记忆。
