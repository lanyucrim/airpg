## 1. 我们最终要做成什么

这是一个由 AI 负责理解和叙述、由程序负责规则与世界事实的长期单人跑团网站。

玩家应该能够：

- 创建角色和战役；
- 用自然语言描述行动与对话；
- 在一个会持续变化的世界中长期游玩；
- 让过去的行为影响 NPC、阵营、任务、通缉和未来事件；
- 查看角色、背包、线索、任务、关系和世界时间；
- 保存、退出并在以后继续游戏；
- 在发生矛盾时追查系统为什么作出某个判定。

项目最重要的目标不是让 AI 每句话都很华丽，而是：

1. 世界事实不会被玩家或 AI 随口改写；
2. 重要历史能够长期保留并在需要时被找回；
3. NPC 只知道自己有理由知道的事情；
4. 过去行为会形成可以追踪的后果；
5. 剧情每轮只推进适当的幅度，并及时把控制权还给玩家。

## 1.1 当前执行方式：模块化开发

本路线图描述项目的总体目标和历史阶段，不直接决定当前改哪个文件。`core`、`map`、`characters`、`items`、`locations`、`behavior`、`story`、`world`、`ai`、`memory` 和 `evaluation` 是同级模块类别；实际开发根据当前任务选择一个开发焦点，不代表固定顺序或模块间完成依赖。

## 2. 永远不改变的权威边界

整个项目必须遵守以下数据流：

```text
玩家原始输入
    ↓
保存原文
    ↓
意图解析与结果性声明清洗
    ↓
权限检查、前置条件检查、规则判定
    ↓
Confirmed Result（确认结果）
    ↓
Confirmed Events（确认事件）
    ↓
更新当前状态投影
    ↓
AI 根据确认结果生成叙述
    ↓
保存 AI 原始输出
    ↓
返回玩家
```

其中：

- 玩家输入是“玩家说过什么”的证据，不是世界事实；
- AI 输出是“AI 叙述过什么”的证据，不是世界事实；
- Confirmed Event 才是“世界中发生过什么”的权威历史；
- Current State 是由事件投影得到的当前状态；
- Summary、Embedding 和检索结果都是可重建的辅助层；
- AI 不能直接操作数据库，也不能直接改变背包、关系、任务或 NPC 状态。

一句话概括：

> 玩家描述意图，系统决定结果，AI 叙述结果。

## 4. 技术路线

### 4.1 前端

- TypeScript；
- React；
- Next.js 兼容的 Vinext/Sites 工程；
- 前端只负责展示、输入和调试，不复制权威规则。

### 4.2 后端

- Python 3.12；
- FastAPI；
- Pydantic 结构验证；
- 领域规则尽量保持为不依赖网络和数据库的纯 Python 函数。

### 4.3 数据库

- 开发初期使用 SQLite，快速验证事件模型和规则；
- 进入长期记忆阶段后迁移到 PostgreSQL；
- 使用 pgvector 保存可重建的事件/摘要向量；
- 不会把向量数据库当成当前世界状态的权威来源。

### 4.4 AI

- 使用可替换的 Model Adapter，不把项目绑定在某一个模型上；
- AI 输出必须使用结构化 Schema；
- 解析失败、超时或输出非法时必须有明确降级路径；
- AI 只负责意图候选、记忆候选、重排和叙述，不直接写权威状态。

### 5.1 阶段 7.5 是一次跨领域重构

7.5 不是在旧搜索分支上继续添加关键词，也不是把 AI 接到现有接口后就宣称获得了开放世界。它是对阶段 1—7 纵向切片的受控拆分：AI 负责自然语言理解、日常机会和 NPC 主观候选；剧本包定义硬边界；Python 权威内核决定是否真的发生。

本阶段必须按“设计冻结 → 领域实现 → 自动验证 → 网页玩家验收 → 投影摘要对比 → 才能切流”的顺序执行。旧事件、旧存档和旧 API 在迁移门通过前继续可用；兼容层只能转发，不能继续增加业务规则。

## 8. 阶段 2：通用回合与原始记录

### 为什么下一步做这个

当前版本已经证明规则边界有效，但很多逻辑仍然专属于“守卫与酒”。在接入 AI 或长期记忆以前，必须先让每个回合都有稳定、可追踪、可重放的数据结构。

### 开发内容

#### 8.1 原始消息存储

增加 `messages`：

- 玩家原始输入；
- AI 原始输出；
- 说话者；
- 战役、回合和世界时间；
- Token 数量；
- 现实记录时间。

原始消息只证明“谁说了什么”，不证明内容是真实世界事实。

#### 8.2 通用命令结构

每个行动统一表示为：

```json
{
  "commandId": "cmd_...",
  "actorId": "player",
  "intent": "request_item",
  "targetIds": ["guard_017"],
  "parameters": {"itemId": "north_gate_key"},
  "claimedOutcome": "success",
  "authority": "system",
  "resolutionRequired": true,
  "sourceMessageIds": ["msg_..."]
}
```

#### 8.3 结果结构

规则引擎统一返回：

```text
status
outcome
confirmed events
visible information
hidden reasons
decision reasons
state version
```

#### 8.4 来源链

形成完整链路：

```text
message
→ command
→ resolution
→ event
→ state projection
→ narration
```

#### 8.5 事务与失败模型

- 全部事件成功后才能提交；
- 任意校验失败不能留下半个结果；
- 重复提交返回原结果；
- 旧版本请求明确返回冲突；
- 非法命令返回结构化拒绝原因。

### 验收场景

- 原始玩家输入可以精确回看；
- 每个事件都能找到来源消息与命令；
- 玩家一句话包含多个动作时能拆分或明确拒绝；
- 角色说谎和玩家越权声明能被区分；
- 任意失败不会产生部分状态变化；
- 事件重放后得到完全一致的当前状态。

### 完成后得到什么

一个可以承接 AI、长期记忆和更多规则的稳定回合内核。

### 当前状态

已完成。实现结果包括：

- 玩家输入与叙述输出原文永久记录；
- 原始消息明确标记为“话语证据”或“叙述证据”，不能作为世界事实；
- 通用 Action Schema 包含玩家声称的结果、决定权和来源消息；
- 每个确认事件都能回指触发它的玩家原始消息；
- 回合详情 API 可以查询命令、消息、事件和版本变化；
- 开发页面可以查看完整来源链；
- 角色内说谎和玩家越权声明可以区分；
- 复合行动按顺序执行，并支持保留已经发生的部分结果；
- 重复提交不会重复写入原始消息或事件；
- 旧 SQLite 数据库可以自动补齐阶段 2 所需字段。

当前本地后端已启用 DeepSeek 纵向切片；未提供密钥的环境仍自动使用本地解析器。真实模型只生成候选命令，权威规则与事件提交路径没有改变。

### AI 调用一：Intent Parser

输入：

- 玩家原始文本；
- 当前允许的动作类型；
- 当前场景可见实体；
- 必要的短期上下文。

输出：

- 一个或多个候选动作；
- 目标实体；
- 参数；
- 玩家声称的结果；
- 角色内对话；
- 解析置信度和歧义。

### Claim Scrubber

把：

```text
我偷到了钥匙
```

转换为：

```text
尝试偷取钥匙
claimedOutcome = success
```

但不会删除原始消息。

### AI 调用二：GM Narrator

AI 只接收：

- 已确认的玩家动作；
- 已确认的结果；
- 玩家可见的原因；
- 当前场景；
- 允许使用的记忆；
- 风格和节奏限制。

AI 不会看到不应泄露给玩家的隐藏原因，也不能产生额外状态变化。

### 4C：有来源上下文中的 AI NPC 决策

首个纵向切片已完成：

- [x] 剧本包 v6 为 NPC 增加私有决策档案，为物品增加经济价值与标签；
- [x] 从权威投影构造 `NpcDecisionContext` v1，而不是把聊天记录直接交给模型；
- [x] 同时提供物品归属、位置、价值、人物经济与性格、风险、六维关系及来源历史；
- [x] 由 AI 在接受、拒绝、还价、延迟和试探中综合选择；
- [x] 要求 AI 引用上下文事实和已确认记忆，禁止直接提出事件；
- [x] 由 Python 复核硬事实、人物底线、记忆来源、允许后果和置信度；
- [x] 接受贿赂只转移真实物品，不会顺带执行“交钥匙、放行、通融”等请求；
- [x] 模型异常或越权时保守降级，并保存不向玩家暴露私有参数的决策审计；
- [x] 模型调用位于数据库写事务外，提交前重新检查幂等键与版本；
- [x] 用成功、拒绝、还价、延迟、试探、底线、虚构记忆、缺少模型和重复提交覆盖第一轮自动测试。
- [x] 建立 11 项版本化《灰港》人物语料和 5 组成对上下文比较；
- [x] 真实 DeepSeek 基线达到 11/11、5/5、零泄漏、零危险副作用，P95 约 1.9 秒。

这不是纯条件系统。Python 计算“什么事实可信、什么后果允许”，AI 综合判断“这个具体人物在当前上下文中会怎么选”。当前历史先使用关系来源和已接受赠礼等精确事件；阶段 5 再增加带来源的混合长期检索。

### 模型失败处理

- Schema 不合法：重试或使用规则解析；
- 模型超时：返回可恢复错误；
- 叙述与确认结果冲突：拒绝输出并重新生成；
- 模型不可用：世界状态保持不变。

### 验收场景

- “我找到了莉娅”只会变成搜索尝试；
- “我对守卫说我有国王批准”会保留为角色说话；
- AI 叙述失败不会让回合重复结算；
- 更换模型不会改变事件与状态规则；
- AI 不能在失败结果中写成玩家已经成功。

- 初始候选；
- 重排分数；
- 被排除的记忆及原因；
- 最终进入上下文的记忆；
- 各分类消耗的 Token。

- 能串联两到三个事件解释当前后果；
- NPC 不会读取不属于自己的秘密；
- 从未出现的信息会回答“不知道”；
- 摘要错误时能从来源事件重新生成；
- 能追查一次“忘记历史”具体发生在哪个检索环节。

## 12. 阶段 6：NPC 认知与后果传播

### 目标

解决“前天做的事为什么今天没有影响”以及“被通缉后为什么所有人都像没事一样”。

### 需要区分的三种状态

```text
世界事实：实际发生了什么
角色知识：某个 NPC 确定知道什么
角色信念：某个 NPC 相信什么，可能是错误的
```

### 信息获得方式

- 亲眼目击；
- 被直接告知；
- 读取文件；
- 阵营通报；
- 传闻传播；
- 调查推断。

每条知识或信念必须带来源。

### 通缉系统

```text
crime.committed
→ witness.observed
→ report.filed
→ wanted.issued
→ faction.notified
→ npc.knowledge_changed
→ npc.attitude_changed
```

这条链路允许出现：

- 犯罪无人目击，因此没有立刻通缉；
- 目击者被说服，没有报告；
- 通缉已经发布，但偏远地区尚未收到消息；
- NPC 知道通缉，却因为欠玩家人情而选择隐瞒；
- NPC 听到错误传闻，对无辜玩家产生怀疑。

### 验收场景

- 没有信息来源的 NPC 不会凭空知道秘密；
- 同一事件可以让不同 NPC 形成不同态度；
- 通缉消息按时间和渠道传播；
- 玩家过去帮助某个 NPC，会影响 NPC 面对通缉时的选择；
- 系统能够解释 NPC 态度变化的来源链。

## 13. 阶段 7：节奏与剧情导演

### 目标

解决 AI 一次把剧情推进太快的问题，同时保留自由叙事。

### 场景状态机

每个场景维护：

- 场景目标；
- 当前阶段；
- 已推进节拍；
- 在场角色；
- 未解决问题；
- 可以触发的事件；
- 结束条件。

### 单回合推进预算

默认一个回合只允许：

- 结算玩家当前明确动作；
- 产生一个主要结果；
- 必要时推进一个场景节拍；
- 提供少量即时反应；
- 把控制权还给玩家。

禁止默认行为：

- 自动替玩家做下一个决定；
- 一次跨越多个地点；
- 一段文字完成整个任务；
- 未经规则判定突然制造重大转折；
- 为了戏剧性让隐藏人物“恰好出现”。

### Story Director

Director 可以提出未来候选：

- 场景压力；
- NPC 计划；
- 未解决线索；
- 可能发生的世界事件。

但候选必须满足时间、地点、因果和权限条件后，才能成为确认事件。

### 验收场景

- 一个简单提问不会自动进入下一章节；
- 玩家采取行动后及时重新获得选择权；
- 场景能够缓慢积累压力；
- 重大事件有可追踪的触发条件；
- Director 的候选不会直接写入世界。

## 17. 每个功能的固定开发流程

以后增加任何功能，都按照下面的顺序执行。

### Step 1：写清行为

先回答：

- 玩家想做什么？
- 谁拥有决定权？
- 需要哪些前置条件？
- 成功、失败和部分成功分别是什么？
- 哪些原因玩家可见，哪些必须隐藏？
- 会产生哪些事件和状态变化？

### Step 2：补充验收场景

至少覆盖：

- 正常成功；
- 前置条件失败；
- 玩家越权声明结果；
- 重复提交；
- 旧状态版本；
- AI 输出非法；
- 事件重放。

### Step 3：定义 Schema 与事件

- 结果结构；
- 事件结构；
- 来源关系；
- Schema 版本；
- 投影规则。

### Step 4：实现纯规则

优先在纯 Python 中实现和测试，不先接数据库、网络或 AI。

### Step 5：接入事务与存储

- 幂等；
- 乐观并发；
- 回滚；
- 重放。

### Step 6：提供 API

API 只暴露稳定的命令与查询，不把数据库结构直接泄露给前端。

### Step 7：接入网页

前端展示：

- 玩家可见结果；
- 重要状态变化；
- 合理的判定依据；
- 冲突与重试提示。

- 单元测试；

## 19. Definition of Done：什么时候一个功能算完成

一个功能只有同时满足以下条件才算完成：

- 行为和权限边界已经写清；
- 成功与失败路径都有测试；
- 重复提交不会重复生效；
- 所有状态变化都有事件；
- 事件有来源并可以重放；
- 前端没有复制权威规则；
- AI 失败不会污染状态；
- 玩家能看懂结果；
- 开发者能追查判定原因；
- 文档已经同步更新；
- 完整构建通过。

“页面上看起来能用”不等于完成。

- 多模型自动编排；
- 强化学习优化检索；
- 大规模战役编辑器；
- 多人联机；
- 3D 地图；
- 复杂战斗动画；
- 没有评估数据支撑的“智能记忆算法”。

这些功能不是永远不做，而是必须等底层事件、状态、来源和测试稳定以后再做。

## 24. 如何使用开发文档

以后每次开始开发前：

1. 先阅读 `docs/development.md`，确认当前开发焦点和边界；
2. 只修改当前焦点及必要的核心协议适配；
3. 完成后删除确认无调用方的过期代码和文件；
4. 运行当前焦点的小范围冒烟测试，并记录范围；
5. 更新当前焦点文档，再决定继续当前焦点或切换到任一同级模块；
6. 不能为了页面效果跳过权威边界。

如果你想知道当前正在做什么，优先看：

- `docs/development.md`：当前开发焦点、边界、验收标准和后续选项；
- `docs/module-classification.md`：正式领域归属和跨模块边界；
- 本路线图：总体目标和历史阶段背景。

只有 `docs/development.md` 持续记录当前焦点和进度；模块归类表仅在实际架构边界变化时更新，本路线图仅在长期目标或历史说明需要校正时更新。
