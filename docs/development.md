## 已完成专题：物品交互与人物能力结算

本轮已完成最小运行链接入，不把 AI 输出当成事实，不新增大而全的物品属性表。自由度由玩家原文和 AI 物理候选提供，边界由程序的实例、位置、身体、能力、目标 resolver 和事件事务提供。

### 设计目标

- 允许玩家提出未被程序逐项枚举的物品交互手段；
- 由 AI 评估工具与目标的物理匹配、基础难度和风险，不让 AI 直接宣布成功；
- 由程序读取人物正式能力、来源状态、身体外伤、可用手和装备状态，完成最终能力检定；
- 只有目标领域已有处理器时，才允许形成效果事件；
- AI、候选生成失败或领域校验失败时，不消耗材料、不改变物品；检定失败按本轮规则推进 1 分钟。

### 已确认的安全边界

```text
玩家行动
→ 行为层建立中性请求
→ 程序检查物品、目标、距离、身体和装备前置条件
→ AI评估物理可行性和工具匹配
→ 程序读取人物能力并完成检定
→ 目标领域验证并构造效果事件
→ 核心事务一次性提交
```

- AI 输出非法、超时、事实不足或描述不一致时，结果为拒绝，不提交 `item.consumed`、`item.created` 或其他状态事件。
- 配方转换继续采用“先构造完整事件计划、再一次性提交”的方式；玩家 `combine_items` 已接入，但只有缓存配方或启用并通过 AI/程序校验的配方才能提交。
- 物理上可行不代表效果已实现。撬锁、粘合、切断和破坏等行为必须等待对应地点、物品或世界处理器。
- 现有人物 `canon`/`player_defined` 能力提供机械加值；`inferred`/`unknown` 按未训练处理，`confidence` 不直接换算成功率。
- 当前主角能力为空时按未训练处理；内伤、生命/专注和轻重伤数值修正不在本轮设计。

## 已实现专题：IT-06 物品耐久损耗与维修

本节记录当前已接入的首版实现。IT-06 只处理有耐久的非消耗物品：工具、服装和装备。一次性消耗品的 `durability` 永远为 `null`；货币、固定家具和普通容器不进入本专题。现有物品契约仍保持 15 个字段，耐久继续使用 `{"current": float, "max": float}`。

### 行为损耗的权威流程

```text
程序确认行为确实接触/施力于物品
→ AI 提出磨损等级、粗略比例、相关能力和物理依据
→ 程序校验候选、类别、描述证据和行为类型
→ d20 + 人物能力修正
→ 程序计算最终损耗
→ 提交 item.wear_applied
→ 投影更新 current
```

AI 不能返回最终损耗、骰点、DC、能力修正、成功结论、事件、物品销毁或维修结果。`estimatedLossRatio` 仅是粗略建议，程序必须按磨损等级和行为上限重新夹逼；`confidence` 只用于审计，不参与成功率或数值乘算。能力 ID 必须来自人物已有资料，不能由模型临时创造。

### AI 磨损候选

候选最小字段固定为：`itemId`、`trigger`、`wearBand`、`estimatedLossRatio`、`abilityId`、`difficultyBand`、`physicalBasis`、`confidence`。磨损等级与基础损耗范围如下：

| 等级 | `max` 的基础损耗范围 |
| --- | ---: |
| `trace` | 0.2%–0.5% |
| `light` | 0.5%–1.5% |
| `moderate` | 1.5%–4% |
| `heavy` | 4%–10% |
| `critical` | 10%–25% |

普通行为单次最多损耗 `30%` 的 `max`。没有明确冲击、撕裂或破坏事实时，候选不得使用 `critical`。物理依据必须能锚定到物品的可观察描述和目标摘要，不能只根据名称猜测。

### d20 与能力对损耗的影响

沿用人物检定规则：`d20 + 能力修正` 对程序映射 DC（`trivial=8`、`routine=11`、`demanding=14`、`hard=17`、`extreme=20`）。

```text
margin = d20 + modifier - DC
最终损耗 = clamp(基础损耗 × 操作质量倍率, 0, 30% × max)
```

操作质量倍率：

| 结果 | 倍率 |
| --- | ---: |
| 自然 1 | 2.00 |
| `margin <= -5` | 1.50 |
| `-4 <= margin <= -1` | 1.25 |
| `0 <= margin <= 4` | 1.00 |
| `5 <= margin <= 9` | 0.75 |
| `margin >= 10` 或自然 20 | 0.50（自然 20 不超过此值） |

行为已有主检定时复用同一次骰点，避免同一行为重复掷骰；只有行为没有主检定但确定会磨损时才单独掷骰。即使操作效果失败，只要程序确认发生了真实接触或施力，仍可产生磨损事件。没有明确行为类型的未知动作不能凭空产生损耗。

### 服装正常穿着

服装的正常日常磨损不逐日调用 AI，也不逐日掷骰。一件服装以约 `180` 个完整穿着日为正常寿命，完整穿着日按 8 小时计算：

```text
日常损耗 = max ÷ 180 × (当日穿着小时 ÷ 8)
```

只在人物实际穿着时累计；放在背包、家具或地面不损耗。撕扯、挂破、剧烈运动等额外事件走 AI + d20 行为损耗流程。天气、受潮、腐坏和环境自动演化不在 IT-06。

### 维修

维修采用与损耗相同的边界：程序确认目标物品、真实维修材料、工具和地点，AI 只提出维修方式与等级，程序用 `d20 + 维修相关能力` 结算。

| 维修等级 | 最多恢复 `max` 的比例 |
| --- | ---: |
| `patch` 临时修补 | 10% |
| `standard` 标准维修 | 25% |
| `major` 大修 | 50% |
| `rebuild` 重制 | 75% |

维修不能提高 `max`，`current` 不得超过 `max`。材料必须是真实物品实例；AI 只能提出材料类别，不能凭空生成材料。维修失败默认不恢复、不消耗材料；维修工具若实际使用，可产生独立磨损。耐久为 `0` 的物品不会自动删除，但必须先通过正式维修才能再次使用。

### 已落地的最小代码单元

```text
items/wear.py                    纯损耗、服装日常损耗和维修数值规则
ai/platform/item_wear.py         磨损/维修候选的底层模型适配器
behavior/commands/maintenance.py 维修命令和玩家行为入口
items/wear_events.py             item.wear_applied / item.repair_attempted / item.repaired 事件
core/projection.py               事件注册、来源和回放校验
world/time.py                    时间推进后汇总服装穿着时长
```

现有 `item.condition_changed` 仅保留历史兼容和状态标签用途，不把它当作新的损耗或维修事件。新增事件必须校验前值、损耗/恢复值、骰点算术、能力来源、来源行为事件、物品类别和幂等关系。

### AI 不可用时的确定性降级

对已经登记的行为类型，程序可使用固定默认磨损等级后继续由程序掷骰和计算：普通工具使用 `light`、强行操作失败 `moderate`、明确冲击 `heavy`、维修工具按维修等级使用 `light` 至 `heavy`、普通服装穿着走日常公式。未登记的自由行为在缺少 AI 候选时安全拒绝，不退化为“玩家描述即事实”。

### 跑团自由度与程序边界

本项目不是把所有动作预先写成固定按钮，也不是把玩家原文交给 AI 后无条件接受。玩家可以用自然语言提出未枚举的尝试；AI 负责在可观察资料范围内提出“可能/不可能/需要澄清”的物理候选；程序负责实例、位置、身体、能力、d20、DC 映射、目标 resolver 和事件事务。只有目标领域注册了 resolver，候选才可能形成真实效果事件。没有 resolver 时，系统保留跑团叙事空间但明确拒绝把描述当成事实。

## 设计稿 v0.1：物品交互与人物能力结算

### 1. 目标与原则

玩家可以提出程序没有逐项列举的动作，例如“用小刀撬锁”“用酒精和棉条制作简易火把”或“用布包住破损玻璃”。AI 负责理解和提供候选，但不能因为玩家提出了动作就把它当成可行事实。最终结果必须同时满足：物品和目标真实存在且可使用；物品描述和功能子契约支持该动作；人物的正式能力、身体和装备状态满足前置条件；目标领域已经实现对应效果；全部状态变化能在一个核心事务中提交。

“AI 说可以”只是待验证候选，不是成功事实；“程序没有处理器”表示玩法尚未实现，不能用叙述文本冒充完成。

### 2. 中性行动请求

行为层把玩家原文转换为不带结论的 `InteractionRequest`。建议字段如下，暂不写入现有事件：

| 字段 | 内容 | 来源/约束 |
| --- | --- | --- |
| `requestId` | 一次行动的幂等标识 | 核心生成或沿用命令幂等键 |
| `actorId` | 行动人物 | 程序确认人物存在 |
| `sourceItemIds` | 主动使用的物品实例 | 程序确认所有权、数量和位置 |
| `targetRef` | 目标物品、家具、地点结构或人物 | 按目标领域解析；未知目标先拒绝 |
| `actionText` | 玩家原文 | 仅用于理解和审计，不直接作为规则 |
| `declaredAction` | `apply`、`combine`、`consume`、`equip` 或 `inspect` | 本地解析或 AI 候选，必须经过白名单校验 |
| `locationId` / `structureId` | 行动发生位置 | 从权威投影读取，不信任前端传值 |
| `expectedStateVersion` | 玩家看到的状态版本 | 核心提交时再次检查 |

请求不携带 `success`、`roll`、`events`、`damage` 或 `durabilityLoss`。请求建立失败时不调用效果处理器。

### 3. 物品和目标摘要

AI 只接收最小、可审计的摘要，不接收可直接写回的投影对象。

`ToolSummary` 使用现有物品契约和功能子契约：`itemId`、名称、完整可观察描述、类别、数量、当前耐久（如适用）、`properties.equipment` 和 `properties.consumable`。材质、结构和尺寸从描述事实读取；不从名称臆测锋利度、硬度、毒性或用途，缺少事实时标记为 `unknown`。

`TargetSummary` 由目标领域提供：目标类型和 ID、可观察描述、公开状态、允许操作白名单、当前阻挡/锁定状态，以及目标领域声明的必要能力。目标摘要不能泄露隐藏事实、私密记忆或未确认剧情信息。

本轮交互只接受已经存在于权威投影中的 `ItemInstance`。`sourceItemIds` 必须能解析到当前实例，并通过所有权、位置、数量、耐久和装备状态校验；只有图册定义、AI 定义候选或叙述中提到的名称而没有实例的对象，不能作为交互输入。日常物品生成、NPC 给予、购买、盗窃和其他获得方式属于物品获取专题，不在本轮重复设计。

物品描述仍是未知日常物品建立定义时的主要物理依据。生成器保存名称、材质、稳定结构、尺寸描述和可观察特征，并将这些内容纳入最终 `description`；但本轮不讨论定义何时生成或实例何时获得。若一次已确认的物品交互产生新实例，`item.created` 只是目标效果事件，不能反过来改变本轮“输入必须是已有实例”的边界。

### 4. AI 物理匹配候选

`ai/platform` 适配器只返回结构化候选，`ai/player` 负责将候选转成玩家可见解释。候选建议为：

```json
{
  "schemaVersion": 1,
  "decision": "possible | impossible | clarify",
  "operation": "apply | combine | consume | equip | inspect",
  "requiredAbilityIds": ["stealth_lock_security"],
  "toolFit": "none | weak | plausible | strong",
  "difficultyBand": "trivial | routine | demanding | hard | extreme",
  "physicalBasis": ["工具有可插入锁芯的细长金属结构"],
  "missingFacts": [],
  "riskHints": ["可能损坏工具"],
  "confidence": 0.82,
  "rejectionReason": null
}
```

程序必须校验字段集合、枚举、能力 ID、物品/目标 ID、物理依据是否能在摘要中找到事实依据、难度是否在目标领域范围内，以及 `possible` 是否有至少一个匹配依据。AI 不得返回骰点、最终加值、成功结论、事件、物品授予、物品消耗或耐久扣除；出现这些字段即拒绝。

`impossible` 和 `clarify` 都不改变状态。`clarify` 只用于缺少关键事实（例如未说明使用哪把小刀），不能把明显不可行的动作拖入检定。

### 5. 人物能力结算输入

人物模块输出只读的 `AbilityCheckInput`，不修改人物档案：

| 输入 | 规则 |
| --- | --- |
| `abilityId`、`level` | 只接受人物能力记录中的 ID 和等级；不临时创造能力 |
| `sourceStatus` | `canon`、`player_defined` 才可能提供机械加值；`inferred` 和 `unknown` 只作上下文，按未训练处理 |
| `confidence` | 只用于审计和澄清，不直接乘到成功率 |
| 身体可用性 | 受伤/缺失的手或手臂不能满足抓握、双手和精细操作；腿脚限制需要移动的动作 |
| 装备状态 | 需要手持时必须有可用手；物品在背包不等于已经拿在手上 |
| 当前耐久 | 作为工具是否可用的前置事实；行为和维修事件按 IT-06 规则更新 |

沿用 `untrained`、`working`、`competent`、`advanced`、`expert` 五档等级。已冻结为 `d20 + 能力修正 >= 程序映射 DC`：`-2/0/+2/+4/+6`；难度 `trivial/routine/demanding/hard/extreme` 映射为 `8/11/14/17/20`。能力为空时按未训练，不能因玩家自称擅长而升级资料。

### 6. 程序检定与效果分派

AI 候选通过后，由核心/行为编排器按以下顺序执行：

1. 重新读取人物、物品、目标、位置、身体和装备状态，确认每个 `sourceItemId` 都是当前投影中的真实实例，并检查数量、权限、可见性、幂等键和状态版本。
2. `toolFit=none`、缺少必要事实、物品已损坏或身体硬限制时直接拒绝，不掷骰。
3. 从候选能力和目标领域允许能力中取交集；没有交集按未训练处理。
4. 使用核心可复现随机源或用户确认的骰制，输入为能力等级、目标难度和明确的情境修正。AI 不参与随机数和最终成功判定。
5. 只有目标领域已有 resolver 时才生成效果计划。配方可生成 `item.consumed` + `item.created`；门锁、破坏和地点变化必须等待地点领域处理器。
6. 先验证整组事件，再在一个事务中提交；任一事件失败，整组回滚。成功后才推进时间或产生玩家可见叙述。

首版支持“成功/失败/需要澄清/身体阻断”。失败检定推进 1 分钟；明确接触/施力的行为会追加 `item.wear_applied`，维修使用 `item.repair_attempted`、`item.repaired` 和材料消耗事件。部分成功、连锁副作用和通用效果仍需逐项 resolver。

### 7. 事件计划边界

交互编排器只生成目标领域声明的事件计划，不直接操作投影。计划至少保留 `requestId`、`actorId`、目标 ID、物品 ID、检定摘要、规则版本和来源事件引用。

- **物品组合**：沿用现有配方的时代、类别、重量和质量守恒校验后，原子提交 `item.consumed` + `item.source_confirmed` + `item.created`。
- **物品消耗**：目标领域先确认效果，再提交已有 `item.consumed`；`requiresDomainResolution` 必须为真。
- **物品状态改变**：明确接触/施力的交互可产生独立 `item.wear_applied`；维修使用 `item.repair_attempted`/`item.repaired`，`item.condition_changed` 不承担新耐久语义。
- **物品与地点/家具**：家具存取已形成转移事件；地点/家具作用只允许已有的审计型效果类型，未实现的开锁、破坏等动作安全拒绝。
- **人物效果**：必须由人物领域提供专门事件，物品模块不能直接修改关系、认知、身体或能力。

### 8. 拒绝、回滚和玩家提示

| 阶段 | 结果 | 状态变化 |
| --- | --- | --- |
| 请求不完整 | `clarify` | 无变化、无时间推进 |
| 物品/目标不存在或无权使用 | `rejected_precondition` | 无变化 |
| 物理匹配失败 | `rejected_physics` | 无变化 |
| 能力检定失败 | `failed_check` | 默认无变化；耗时待决定 |
| 目标领域未实现 | `unsupported_effect` | 无变化，不以叙述冒充成功 |
| 事件计划提交失败 | `transaction_failed` | 全部回滚 |
| 检定成功 | `succeeded` | 仅提交已验证的目标领域事件 |

玩家可见叙述必须引用实际结算状态。被拒绝时明确说明没有消耗物品、没有改变世界状态；成功时不得添加计划外物品、事实、对话或伤害。

### 9. 首批实现建议和验收

首批已实现三个最小分支：**物品组合（配方 resolver）**、**物品↔家具存取（确定性容量/位置校验）**、**物品↔地点/家具作用交接（仅允许已登记效果类型）**；本轮又接入 **行为磨损、服装日常磨损和维修**。所有分支都经过物品交互或耐久审计事件；组合新日用品必须带 `item.source_confirmed`，再创建实例。门锁、破坏和通用消耗品效果仍不冒充完成。

必须覆盖：合法组合成功；物理不匹配、缺少能力、`inferred` 能力、手部受伤或工具不在可用容器时拒绝；AI 越权字段、错误物品 ID、虚构能力、低置信度或描述无依据时拒绝；重复 `requestId` 不重复消耗/创建；事务任一事件失败时原料、产物和人物状态完全不变；AI 不可用时仅允许已有确定性配方缓存，不能退化为“玩家说了算”。

### 10. 已确认的运行规则

1. **检定制**：`d20 + 能力修正 >= 程序映射后的 DC`。
2. **取用方式**：允许从背包自动拿起工具，必须在玩家可见叙述和交互审计中反馈；不等于永久装备绑定。
3. **首批效果**：同时纳入物品↔物品组合、物品↔家具、物品↔地点。
4. **失败语义**：检定失败推进 1 分钟；确实发生接触/施力的失败行为仍可按独立损耗规则结算，维修失败不恢复或消耗材料但实际使用的工具可损耗。
5. **能力证据**：`canon` 与 `player_defined` 都提供机械加值；`inferred`/`unknown` 不提供。

### 本轮明确不做

- 不实现前端专用打造面板、通用 `use_item` 效果或未注册 resolver 的物品连接关系；自然语言组合命令仅走已校验配方链；
- 不修改正式物品 schema 7 的 15 个字段；
- 不恢复或扩展 `item.used` 的权威效果；
- 不新增力量、敏捷、智力等人物属性；
- 不实现门锁、地点访问、通用物品效果和交易；这些仍需各自领域 resolver。IT-06 的耐久损耗与维修首版已经接入。
- 真实 DeepSeek 调用只在明确的低次数冒烟/全量验证中启用，不作为状态权威。

## 已开发实现的功能

### 核心基础

- Python 后端是唯一权威状态来源；玩家输入、前端和 AI 都不能直接修改状态。
- 玩家输入先进入命令与行为解析，重要变化必须形成经过校验的事件。
- 投影可以从事件回放重建当前状态，快照和读模型不是第二套事实来源。
- 命令支持幂等标识和状态版本检查，避免重复点击或重试造成重复结算。
- 已有 SQLite、PostgreSQL 存储实现，以及战役状态、回合提交和地图只读 API。
- 前端只消费后端公开读模型，不复制最终移动、物品所有权、装备或外伤判定。

### 人物模块

- 灰港人物图册当前有 142 条运行时人物档案，保留资料来源和 Canon/推定状态。
- 每个人物拥有独立背包容器；人物位置、背包和物品所有权可以通过事件与投影重建。
- 已有关系、认知和知识的基础事件与投影；开局会映射少量有明确来源的关系事实。
- 5 条作者日程会编译为 `npc.schedule_defined`，并用于“找人”时计算预计位置；查询本身不会移动人物。
- 已定义约 53 类能力和 215 条人物能力记录；能力带来源、可信度、依据和引用。
- 所有人物均有语言风格字段；无法判断的值保留为空或 `unknown`，不会由 AI 补造成 Canon。
- 身体模型覆盖头部、躯干、左右手臂、左右腿、左右手和左右脚等部位。
- 已有手持、穿戴、单双手和装备槽位校验。
- 已有外伤应用、清除和肢体缺失事件；手臂/手部外伤会限制取物和手持，腿脚外伤会限制移动。
- NPC `offer_item` 已形成有限决策链：读取 NPC 私有上下文和物品正式 `valueCrown`，未知或非正价值安全拒绝，非法模型候选不能提交状态。

### 物品模块

- 当前正式契约为 schema 7 的 15 字段定义/实例模型；物品种类和具体实例分开保存。
- 灰港正式图册当前有 40 个定义和 6 个实例。
- 已有物品创建、转移、消耗、状态改变、丢弃、销毁等事件基础和投影处理。
- 已有普通容器、人物背包和固定家具容器；容量、物理位置和所有权可以校验。
- 未知重量或体积不会被当成 0 绕过容量规则。
- 已有装备子契约、单双手规格和穿戴槽位，不按物品名称猜测装备方式。
- 已有通用消耗品资料契约；消耗品效果候选不能绕过人物、地点或世界领域确认。
- 玩家现金已冻结为背包或自有容器中的可堆叠 `currency` 实体物品，不再保留数值钱包余额。
- 初始耐久使用 float；只有非消耗工具、服装和装备实例使用耐久，一次性消耗品为 `null`。
- 初始耐久 AI 以崭新小刀 `100.0` 为基准提出受限候选，程序负责类别锁定、比例、上限和最终换算；主角小刀当前为 `85.0/100.0`。
- AI 日常价格/重量参考、日常物品定义、严格配方候选、时代限制、定义复用和缓存已经实现为资料或候选工具。
- 日常物品定义候选已升级为 schema 2：生成名称、材质、稳定结构、粗略尺寸、可观察特征和未知事实；程序要求这些内容完整保存在现有 `description` 中，不扩充正式 15 字段物品契约。
- 苹果 10 克朗是价格参考基准；重复日常物品优先读取缓存，不重复调用 AI。

### 地图与地点模块

- 灰港图册包含 96 个顶层地点、45 条街道、128 条有向地点链接和 474 个内部结构。
- 七个大区只作为区域元数据，不是玩家可以停留或进入的地点。
- 街道是无内部结构的通行节点，不拥有“主要使用区”等建筑房间。
- 建筑保留为地点聚合和街道入口；玩家抵达建筑时最终落到具体普通内部结构。
- 玩家只能沿当前权威相邻出口移动；同街地点也按实际连接与时间通行，不会一分钟到达所有地点。
- 当前地点显示完整的区域、地点和内部结构名称。
- `access` 已类型化为 `public`、`private`、`hidden`；普通和 `private` 结构保持开放。
- 隐藏结构不再按中文名称猜测；无正式发现绑定时不会生成玩家入口。
- 不可见出口必须绑定有效 `discoveryId`；已有发现、钥匙锁和剧情条件的基础判定。
- 运行时地点、结构和街道 ID 已集中到 `map/runtime_ids.py`；无来源伪旧 ID 已删除。
- 已有只读步行/马车路线估算；查询不会直接产生移动事件。
- 每个真实内部结构有 1 至 3 个固定家具容器，当前共 1422 条；街道、区域和城市不生成家具。
- 家具名称、描述、类型、结构绑定、容量和固定性会在开局通过 `container.created` 事件物化。

### 世界天气与地点联动

- 程序定义季节允许天气、温度范围和最大日温差。
- AI 每日只生成结构化天气候选；程序校验通过后才提交天气确认事件。
- 非法天气候选会被拒绝，不会写入投影。
- 天气只影响跨顶层地点移动；同一地点内部结构移动加时固定为 0。
- 出发前后端提供基础时间、天气预计加时和预计总时间，实际移动复用同一套规则。
- 玩家端显示“基础时间 + 当前天气预计加时 = 预计总时间”。

运行时代码已经具备：

- 每日天气候选。
- 物品行为磨损候选和维修等级候选；模型只返回物理建议，程序完成 d20、数值和事件结算。

显式资料工具已经具备：

## 已冻结的设计决定

- **模块并列**：模块按类别开发，当前焦点不是前后阶段顺序。
- **权威边界**：经过校验并提交的事件才是事实；玩家输入、AI、图册和叙述都不能直接改状态。
- **人物资料**：能力和语言风格是带来源的上下文，不自动成为判定或 Canon；未知值保持空。
- **地图层级**：大区是元数据，街道是无内部结构的通行层，建筑是聚合/入口，玩家最终位于具体内部结构。
- **结构访问**：普通和 `private` 结构默认开放；只有显式 `hidden` 结构或带 `discoveryId` 的不可见出口使用发现门控。
- **天气移动**：只有跨顶层地点移动叠加天气时间，内部结构移动加时为 0。
- **物品契约**：定义与实例分离；当前正式物品契约为 schema 7。
- **实体货币**：玩家现金只来自自有容器中的 `currency` 实例及其 `quantity`，不存在独立数值余额。
- **耐久**：float 耐久只用于非消耗工具、服装和装备；腐坏、受潮和环境时间演化不设计。
- **IT-06 耐久规则**：行为损耗由 AI 提出磨损候选、程序校验并以 `d20 + 能力修正` 计算；普通服装按 180 个完整穿着日缓慢损耗；维修有独立等级和事件；AI 不得返回最终损耗或维修结果。
- **AI-物品**：AI 只能产生受限定义、参考、配方和初始耐久候选，不能凭空创建实例、授予物品或确认效果。
- **家具**：家具是地点结构资料和固定容器，不是可携带物品；AI 候选必须经过完整图册校验和开局事件物化。
- **清理**：无调用方或被正式实现替代的代码应删除；历史事件兼容必须有明确用途，不能依靠旧业务文件长期兜底。
