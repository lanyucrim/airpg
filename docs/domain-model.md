# 领域模型

## 1. 总体边界

第一版采用模块化单体。模块可以在同一 Python 应用中运行，但必须通过明确接口协作。

```text
Turn 回合协调
├── Intent 意图与实体解析
├── Scene 场景和节奏
├── Inventory 物品与容器
├── Rules 行动与检定
├── Relationship 个人关系
├── Knowledge 角色认知
├── Reputation 群体声望
├── Law 犯罪与通缉
├── Story 剧情线和时钟
├── Affordance 地点机会与日常自治
├── Event 事件与投影
└── AI 结构化提议与叙述
```

`Turn` 负责顺序和事务，不直接实现每个领域的业务规则。

## 2. 核心实体

### ScenarioPackage

剧本包是不可变、带版本的初始世界模板，包含地点、角色、组织、容器、物品、关系、客观事实、线索、时钟、义务、初始场景和作者定义的调查交互。它不是运行中的存档，也不能直接修改当前状态。

创建战役时必须先校验剧本包，再把它编译成初始确认事件。存档固定记录 `scenarioId`、`scenarioVersion` 和 `scenarioContentHash`；后续更新同名剧本包不会静默覆盖旧存档。

### Campaign

战役是数据隔离和事件排序的根边界，包含：

- 当前世界时间；
- 世界时间刻度单位和用于显示的战役历法；
- 当前状态版本；
- 使用的规则配置；
- 玩家角色；
- 当前场景；
- 事件序列。
- 创建时使用的剧本包标识、版本和内容指纹。

### Character

玩家与 NPC 共享基础角色模型，但权限不同：

- 身份和外貌；
- 所在位置；
- 属性与状态；
- 所属阵营；
- 目标和行为约束；
- 可用认知；
- 持有容器。

AI 不能把 NPC 的隐藏字段直接展示给玩家。

### Location

地点包含：

- 父级和相邻地点；
- 进入条件；
- 可见实体；
- 地区和法律管辖；
- 场景可用环境信息。
- 地点机会集合（`WorldAffordance`），用于描述交易、用餐、工作、休息、社交、观察和普通资源搜索的合理可能性。

地点机会不是确认事实。它必须绑定来源、时间规则、参与者、资源模板和故事影响等级，供 AI 提出候选，再由程序校验并生成事件。

阶段 3C 的出口至少包含目标地点、移动耗时和初始可见性。角色只能通过当前地点的可见直连出口移动；“我去了某处”只是行动意图，不能产生瞬移。

### Organization

组织与角色分开存在。首领死亡不会自动删除组织，成员也不等于组织资产。组织可以拥有总部、领导者、成员、资源标签、政策边界和私有目标，并有独立的玩家可见性。

### Clock 与 Obligation

`Clock` 表达统一世界时间上的期限；`Obligation` 表达债务、承诺、合同或职责，并引用债务双方、到期时钟和证据事实。二者都由初始事件或后续确认事件建立，不能只存在于叙述文字里。

### ItemDefinition 与 ItemInstance

定义描述“这种物品是什么”，实例描述“世界中具体哪一件”。

唯一物品始终使用实例；同类消耗品可以在不丢失来源和状态的前提下按批次数量管理。

物品定义必须声明 `criticality`（`mundane`、`contextual`、`story_bound`、`major_key`）和 `storyBindingPolicy`。AI 日常候选只能默认生成 `mundane` 实例，不能直接生成 `major_key`。

物品实例必须保留来源事件、当前容器、所有者、数量、状态、过期时间和最近变化事件。普通物品参与故事时，必须通过独立的故事绑定事件，并保留原始来源。

### WorldAffordance 与 RoutineEventProposal

`WorldAffordance` 表达地点在特定时间和条件下可提供的行动机会；`RoutineEventProposal` 是 AI 根据机会提出的候选结果。候选不是事实，不能直接修改投影。

日常候选必须带有 `narrativeWeight` 和 `storyImpact`（`none / soft / story / major`）。没有剧本触发条件的日常候选只能产生 `routine` 或受限 `soft` 结果，例如时间消耗、普通物品、交易、用餐和小幅社交影响。

### Container

所有物品必须位于明确容器中，例如：

- 角色背包；
- 角色手部；
- 房间地面；
- 木箱；
- NPC 私人物品栏。

物品转移本质上是容器之间的受验证转移。

### Scene

场景包含：

- 地点；
- 参与角色；
- 当前阶段；
- 可交互实体；
- 当前目标和威胁；
- 节拍预算；
- 转场条件。

### IntentParseAttempt

意图解析尝试是非权威审计实体，记录解析来源、模型标识、模型可见请求、原始结构化输出、失败代码和对应回合。它用于评估、排错和证明模型看到了什么，但不参与事件重放，也不能成为世界事实来源。

普通玩家接口只返回脱敏后的解析状态；原始载荷仅供后端内部审计。

### Inspection 与 Inquiry

`Inspection` 表达角色可以对真实物品进行的检查，必须声明访问策略、可能获得的事实、线索和耗时。`Inquiry` 表达向具体 NPC 询问一个话题，必须声明 NPC 知识前提和允许披露的事实。

两者都是剧本定义，不是已经发生的剧情。只有通过前置条件并提交 `item.examined` 或 `npc.answer_given` 等确认事件后，角色知识和玩家线索才会改变。`interaction.completed` 用于防止相同交互重复产生同一结果。

### Relationship

关系是有方向的：

```text
guard_017 → player
player → guard_017
```

初始维度：

```text
favor
trust
fear
respect
suspicion
debt
```

每次变化必须保存来源事件。

关系维度只能作为 NPC 决策输入之一。NPC 决策还必须考虑自身认知、资源、人格、动机、恐惧、风险、职责、日程和当前请求，禁止用单一好感阈值直接决定借贷、隐瞒或重大帮助。

### WorldFact、Knowledge 与 Belief

三者分开：

- `WorldFact`：客观事实；
- `Knowledge`：角色通过观察或传播获得的信息；
- `Belief`：角色当前相信的命题及置信度，可能错误。

角色决策只能读取该角色的认知视图，不允许直接读取所有世界秘密。

### Reputation

声望以“评价主体范围 + 被评价身份”为键，例如：

```text
灰港城居民 → 玩家公开身份
盗贼公会 → 玩家别名
城卫队 → 未知黑发嫌疑人
```

不同身份可能尚未被社会认定为同一个人。

### LegalCase 与 WantedRecord

法律系统需要分别表达：

- 犯罪事实；
- 证据；
- 目击者陈述；
- 嫌疑身份；
- 特定管辖区的通缉记录。

犯罪发生不必然导致实名通缉。

## 3. 聚合与一致性边界

第一版以单个战役回合为事务边界。一次提交可以同时写入多个领域事件，但必须由回合协调器统一校验和提交。

必须强一致的变化：

- 物品来源与目标容器；
- 资源消耗与行动结果；
- 骰子结果与判定事件；
- 关系变化与来源事件；
- 世界时间与需要耗时的行为；
- 命令幂等状态与事件提交。

可以稍后异步生成的内容：

- 文学化叙述；
- 长期摘要；
- 语义向量；
- 非关键分析指标。

## 4. AI 权限边界

| 能力 | AI 可做 | AI 不可做 |
|---|---|---|
| 意图解析 | 提取行动、目标、方式和原话 | 假定引用实体存在 |
| 导演 | 在许可结果中选择 NPC 反应 | 改写骰子或规则结果 |
| 日常自治 | 从已编译地点机会中提出普通行动和结果候选 | 创建无来源地点、人物、任务、关键物品或重大剧情后果 |
| 记忆摘要 | 压缩已发生事件 | 创造未发生的历史 |
| 叙述 | 描写玩家可感知的已提交结果 | 创建物品、知识或状态 |

## 5. 当前纵向验收场景

固定初始状态来自《灰港：黑潮王座》：

```text
主角位于白鹭屋一楼大厅
铁钩帮最后通牒真实存在于桌面容器
白鹭屋营业账本真实存在于地点记录容器
地窖暗道客观存在，但开局只有玛莎和奥蒂斯知道
暴雨尚未暴露暗道入口
```

需要依次验证：

1. 查看最后通牒必须检查桌面上的真实物品，且不会改变物品归属；
2. 玛莎只在同一地点回答，并且只能披露她当前知道的事实；
3. 核对账本只揭示债务数字异常，不会接受玩家声称的伪造者；
4. 一个复合输入不能超过当前场景的主要节拍预算；
5. 玩家只能沿可见直连出口从大厅进入厨房和地窖；
6. 玩家提前说出暗道名称不能创建发现事实；
7. 暴雨条件成立前搜索地窖只产生调查与耗时；
8. 权威条件成立后调查提交出口发现、知识和线索事件；
9. 发现后玩家才能从地窖穿过排水通道；
10. 同一发现命令重复提交只生效一次；
11. 已知发现再次调查不会重复创建线索；
12. 重放事件能够恢复相同的角色知识、调查完成状态和出口可见性。

门锁能力另用纯规则状态验证：缺少权威钥匙时拒绝，钥匙确实位于行动者容器时才允许通过。正式灰港内容不会为了测试而虚构原稿未声明的上锁房门。
