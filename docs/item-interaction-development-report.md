# 物品交互与人物能力结算开发报告

更新日期：2026-08-26
范围：人物、物品、地点三大模块及其直接交融；不包含贸易、人际网络、世界自治、内伤和耐久损耗。

## 结论

本轮已形成一条可回放的最小跑团交互链。玩家可以用自然语言提出没有预先做成按钮的物品动作；AI 只对当前可观察资料提出物理候选，程序再完成前置校验、人物能力检定和目标领域事件计划。AI 不能把玩家的愿望直接变成成功事实。

核心判定固定为：

```text
d20 + 能力修正 >= 程序映射后的 DC
```

能力修正为 `untrained -2`、`working 0`、`competent +2`、`advanced +4`、`expert +6`。只有 `canon` 和 `player_defined` 来源状态享受等级修正；`inferred` 和 `unknown` 按未训练处理。难度档由程序映射为 `trivial 8`、`routine 11`、`demanding 14`、`hard 17`、`extreme 20`。

## 已实现模块

### 人物能力检定

文件：`apps/server/src/trpg_server/characters/checks.py`

- `AbilityCheckInput` 从人物正式能力资料生成只读检定输入。
- `PhysicalRequirements` 在掷骰前检查手、手臂、腿、脚和指定身体部位。
- `resolve_ability_check` 使用显式随机源，记录骰面、修正、DC、总值和差值。
- 身体硬阻断不消耗随机数；能力缺失不会被玩家原文临时创造。
- 模块不依赖网络、数据库或投影写入。

### 物品交互契约

文件：`apps/server/src/trpg_server/items/interaction.py`

- `InteractionRequest` 表达行动者、物品实例、目标类型、操作和原文。
- `ItemInteractionCandidate` 严格约束 AI 输出字段、枚举、能力白名单、置信度和物理依据。
- AI 不得返回骰点、DC、事件、物品创建/消耗、耐久扣除或最终成功结论。
- `validate_candidate_evidence` 要求物理依据能够锚定到传入的可观察摘要；无法锚定时拒绝。

### 来源确认与未知日常物品

文件：`apps/server/src/trpg_server/items/provenance.py`

动态日常物品只有在以下来源之一被确认后，才能作为正式实例进入交互：

`location_take`、`furniture_take`、`npc_transfer`、`purchase`、`theft`、`recipe`。

来源通过 `item.source_confirmed` 事件审计，随后才允许 `item.created`。图册定义、AI 定义候选、叙述文字和玩家自称都不能直接生成实例。投影还会拒绝没有来源确认的 `daily_*` 定义实例。既有非动态历史实例保留回放兼容。

### 行为编排与路由

文件：

- `apps/server/src/trpg_server/behavior/item_interactions.py`
- `apps/server/src/trpg_server/behavior/router.py`
- `apps/server/src/trpg_server/behavior/commands/items.py`

编排顺序：

1. 本地解析玩家原文，建立中性请求。
2. 从权威投影确认实例、来源、所有权、当前位置、目标家具/地点和容量。
3. 没有永久手持绑定时，允许从背包自动拿起，并在玩家叙述和审计事件中反馈；不自动写入永久装备绑定。
4. 对组合和地点作用调用物品交互适配器；家具直接存取走确定性程序路径。
5. 对需要检定的动作执行人物身体前置和 d20。
6. 只有目标 resolver 返回完整事件计划后，才提交交互审计、效果/转移、产物和时间事件。

### 首批三类交融

| 交融 | 当前实现 | 状态边界 |
| --- | --- | --- |
| 人物 ↔ 物品 | 背包所有权、自动拿起、手部阻断、能力检定、组合输入 | 装备/穿戴已有独立模块；耐久损耗未做 |
| 物品 ↔ 家具 | 家具容器位置、可见性、容量、存入和取出 | 权限、锁、私人物品和家具破坏待地点专题 |
| 物品 ↔ 地点 | 当前结构目标摘要、物理候选、地点效果审计事件 | 未注册的开锁、破坏、照明等具体效果安全拒绝 |
| 人物 ↔ 物品 ↔ 地点 | 当前结构内使用工具、家具取物后使用、位置联动 | 不直接修改人物关系、认知或世界法律状态 |

## 事件与回放

新增/接入的事件：

- `item.source_confirmed`
- `item.interaction_resolved`
- `location.item_effect_applied`
- 既有 `item.transferred`、`item.consumed`、`item.created`
- 检定失败时的 `time.advanced`

交互处理器已在 `core/projection.py` 注册。交互审计先于地点效果；地点效果必须引用同一交互、同一来源物品，并且交互状态必须为 `succeeded`。重复来源确认、重复交互 ID、重复效果 ID 和错误因果顺序都会在回放时拒绝。

## AI 的职责和限制

新建 `apps/server/src/trpg_server/ai/platform/item_interaction.py`：

- DeepSeek 请求只包含当前实例的可观察摘要和目标摘要。
- `temperature=0`、JSON 模式、低 token 上限、单次/受限重试。
- HTTP 错误、超时、无效 JSON 和越权字段都安全降级。
- 环境变量 `TRPG_ITEM_INTERACTION_MODEL_ENABLED` 未开启时，任意未缓存自由组合不会被当作成功；已有确定配方缓存仍可进入程序验证。
- 真实模型不写存储、不调用投影、不提交事件。

这保留了跑团的开放表达，同时把事实和结果留在程序框架内：AI 可以提出新尝试，但不能凭空补充物品、地点、能力、骰点或效果。

## 测试与验证

本轮交互与人物检定定向集合：`48 passed`（4 个测试文件）。当前开发文档范围的程序回归为 `318 passed`（36 个测试文件，去重执行）。

覆盖内容：

- d20 成功、失败、身体阻断和来源状态修正；
- AI 适配器 JSON、HTTP 错误、密钥不泄露和低 token 请求；
- 检定审计字段白名单、d20/DC 算术、状态映射和伪造成功阻断；
- 交互事件注册、严格载荷、因果顺序、重复提交和回放一致性；
- 未确认日常物品拒绝、来源确认后创建；
- 自动拿起反馈、家具存入、容量前置和本地自然语言路由；
- 现有人物身体/装备、物品配方、架构边界和投影迁移回归。

服务/API/回合历史测试不属于本轮当前模块范围。真实 DeepSeek 采用低次数、非持久化冒烟：NPC 决策通过（2331 tokens）、物品价格/重量通过（349 tokens）、物品交互候选通过（522 tokens）、日常物品定义通过（1203 tokens）、配方判断通过（1449 tokens）、天气通过（443 tokens）。沙箱内日常物品请求曾因网络权限失败，未产生写入；获授权后只重试一次并通过。所有请求均未写入事件库、图册缓存或玩家存档。

## 尚未完成

- 地点领域尚未提供开锁、破坏、修理、照明等具体 resolver；当前只保留安全的效果交接边界。
- 通用 `use_item` 和消耗品实际效果仍需人物/地点专门事件。
- 组合目录仍需逐步补齐；非消耗工具产物的初始耐久需要单独设计。
- 家具权限、锁、私人财物、隐藏结构和搜索发现需要地点专题。
- 工具损耗、维修、内伤、生命/专注、交易和剧情物品的正式确认移除流程明确不在本轮；直接销毁剧情物品已由后端安全拒绝。
- NPC、叙述和日常模型的部分底层适配器仍在原领域文件，后续可按 AI 双层架构继续迁移，但本轮不改变其事件语义。

## 权威边界复核

玩家输入、AI 候选、叙述文本、图册定义和记忆检索都不是权威状态。只有通过领域校验并由核心事务提交、可由事件重放得到的结果，才会改变人物、物品或地点状态。
