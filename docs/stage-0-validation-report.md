## 2. 反方审查与修正

### R-01 玩家发言可能污染历史

风险：玩家说“前天送过酒”，系统将其写成过去事实。  
修正：回合协议明确先记录发言，再查询历史；不存在匹配事件时只能进入误记、欺骗或信念流程。

### R-02 AI 叙述可能绕过物品系统

风险：叙述写出“交出钥匙”，但数据库没有转移。  
修正：叙述器只能读取已提交事件；物品所有权仅由 `item.transferred` 投影改变。

### R-03 记忆检索可能把相似文本当成事实

风险：向量检索到相似的送礼段落，就错误增加好感。  
修正：上下文规范要求先使用实体、事件类型和时间精确检索，摘要与叙事仅作补充。

### R-04 世界时间表示含糊

风险：日期字符串、现实时间和剧情时间混用，导致期限与传播顺序不一致。  
修正：权威世界时间统一为战役纪元起的整数刻度，显示历法单独处理。

### R-05 复合命令并非总是全成全败

风险：玩家已经说出一句话，但递交不存在物品失败；若整个回合回滚，NPC 会不合理地“没听见”。  
修正：复合命令按顺序拆分组件，失败组件不能成功，但已经成立的独立发言可以提交。

### R-06 叙述失败发生在事实提交之后

风险：玩家看不到已发生结果，重试又可能重复执行。  
修正：叙述重试只读取原事件；持续失败时返回确定性简短说明，不重做命令。

### R-07 Next.js 与 Python 可能形成双后端

风险：部分游戏规则被写入 Next.js 服务端功能，产生两套事实来源。  
修正：ADR 明确 Next.js 是界面层，Python 是唯一领域权威；前端不得计算最终状态。

### R-08 大型项目可能过早微服务化

风险：一个回合跨多个服务，物品、关系和时间难以保持一致。  
修正：第一版采用 Python 模块化单体，以战役回合作为主要事务边界。
