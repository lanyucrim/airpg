# 阶段 7 设计与开发流程：节奏、导演与旧版世界自治基线

状态：已完成（导演边界、旧版 V3 编译和网页玩家界面基础；内容源已由 7.5A 切换到 V4.2）

## 设计边界

Director 只能产生 `DirectorProposal` 和 `WorldEventCandidate`，不能直接改投影。候选必须经过地点、世界时间、来源、权限、重复提交和节拍校验后才能成为 `world.reported`。默认每回合只结算一个主要结果；等待、工作、发呆、失败和空搜索都是真实可提交的回合。

## 开发流程

1. 扩展场景状态以保存未解决问题、结束状态、场景压力、参与者计划和主要节拍预算；场景结束前不替玩家决定承诺、态度或下一步。
2. 为日、周、月和年边界定义独立候选。结算使用前后世界时间区间，而不是只判断“当前时间是否整除”，避免一次等待跨过多个周/月边界时漏报。
3. 编写旧版 V3 Markdown 编译器，输出 `v3-catalog.json`。该目录只用于历史存档兼容；新战役由 7.5A 的 V4.2 编译器输出新目录。条目包含分类、标题、原稿行号、来源片段指纹和全文源指纹；运行时只加载结构化目录。
4. 编译七城区、建筑索引、组织轨迹、NPC 个人时钟、36 个月时间轴、周历、慢燃事件、随机事件、94 条支线和终局目录。完整地图仍由 JSON 剧本包提供地点层级、出口和物品容器归属。
5. 普通环境搜索、物品取用、人物寻找与隐藏通路调查使用不同命令。厨房搜索只返回真实容器中的食物；取用另一个回合提交 `item.transferred`；秘密通道继续受 discovery 条件控制。对擦拭、整理、打扫等合理但未写入剧本的日常行动，使用有地点来源的通用环境事件并只推进少量时间，不凭空改变物品、关系或剧情。
6. 玩家可以明确等待一周或一个月；权威时间结算允许跨越多个周/月边界，并逐个提交对应城市周报和月度结算候选。
7. 玩家网页默认只展示地图、场景、人物、出口、背包、公开期限、线索、未解决问题和周报。来源链、模型请求和检索轨迹只有 `?mode=developer` 受控入口可见。

## 研究依据与验收

节奏设计参考 Generative Agents 的日程/环境连续性、LongMemEval 的长期更新与拒答划分，以及 Memory-Driven Role-Playing 的 Anchoring–Selecting–Bounding–Enacting 边界思想；这些论文只影响候选和上下文组织，不能越过事件权威层。

旧 V3 编译验收：7 个城区、16 个组织、20 个 NPC 时钟、36 个时间轴条目、94 条支线，源文件指纹可重建。该结果只作为历史基线。V4.2 的完整编译验收由阶段 7.5A 重新定义。导演验收覆盖提议不改状态、非法候选拒绝和跨越 4 个周边界加 1 个月边界的长等待。
