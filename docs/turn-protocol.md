# 单回合执行协议

## 1. 目标

单回合协议保证自然语言输入不会绕过游戏规则，并保证每次行动可验证、可重试、可解释和可回放。

## 2. 回合状态

```text
RECEIVED
  → PARSED
  → VALIDATED
  → RESOLVED
  → COMMITTED
  → NARRATED
  → COMPLETED
```

任一提交前阶段都可以进入 `REJECTED` 或 `NEEDS_CLARIFICATION`。提交后叙述失败时进入 `NARRATION_FAILED`，不能回滚已经发生的游戏事实。

## 3. 标准流程

### T-01 接收

记录：

- `turn_id`；
- `command_id`；
- `idempotency_key`；
- 战役和玩家标识；
- 玩家原始输入；
- 客户端看到的状态版本；
- 接收时间。

### T-02 分类和意图解析

将输入分类为：

- 游戏行动；
- 角色发言；
- 行动与发言组合；
- 界面或系统命令；
- 需要澄清的输入。

自然语言解析只生成候选命令，不读取或修改数据库。模型只能接收后端组装的玩家可见解析上下文；其输出必须先通过严格 Schema、可见实体、权限和参数校验。模型超时、输出非法、要求澄清或置信度不足时，回合安全降级到本地解析器，不能因为解析失败创建世界事件。模型网络调用在数据库写事务之外执行；正式提交前必须重新检查幂等键和世界版本。

一次输入包含多个部分时，应解析为有顺序的复合命令。例如“我提醒他酒的事，然后递出酒”至少包含 `speech` 和 `offer_item` 两个组件。每个组件分别验证，后续组件可以依赖前一组件结果。

### T-03 实体解析

把“那瓶酒”“门口的守卫”等引用解析为具体实体标识。解析顺序：

1. 当前场景中的精确匹配；
2. 玩家可见或可访问实体；
3. 最近明确提及的实体；
4. 唯一合理候选；
5. 多个重要候选时请求澄清。

实体解析采用风险敏感策略：闲聊中的轻微歧义可以合理推断；转移唯一物品、消耗稀缺资源、攻击目标或作出不可逆选择时，无法唯一解析就必须澄清。

### T-04 加载上下文

按精确关系加载：

- 当前场景和世界时间；
- 行动者与目标状态；
- 相关物品和容器；
- 双方关系；
- 适用的法律、声望和规则；
- 与当前行动直接相关的历史事件；
- 各角色可用的认知。

语义检索只能补充叙事记忆，不能替代这些精确查询。

### T-05 前置条件验证

验证身份、位置、所有权、数量、访问权限、状态版本、行动能力和目标是否存在。失败的命令组件不产生其声称成功的事件。

复合命令可以产生部分结果。例如玩家已经当众说“这瓶酒给你”，随后才发现背包中没有酒，则 `speech.spoken` 可以成立，`item.transferred` 不能成立。回合必须逐项返回结果，不能把失败组件伪装成成功。

### T-06 规则判定

确定性规则先计算：

- 是否需要检定；
- 骰子或随机结果；
- 资源和时间消耗；
- 关系、声望和法律修正；
- 允许的结果等级；
- 允许 AI 选择的候选反应。

随机结果必须被记录，以便重放和审计。

### T-07 导演提议

只有当规则允许多种合理表现时才调用导演。导演输出必须是结构化提议，并明确：

- NPC 选择；
- 允许揭示的事实；
- 建议事件；
- 推进的节拍数；
- 是否请求转场。

导演不能增加玩家未拥有的资源，不能改变已经确定的骰子结果，不能让 NPC 使用未知信息。

### T-08 校验

校验器检查所有拟提交事件：

- 事件类型是否允许；
- 引用实体是否存在；
- 事件是否满足领域不变量；
- 物品是否发生重复转移；
- 角色是否拥有所用知识；
- 状态变化是否超过规则许可范围；
- 是否擅自替玩家行动；
- 是否超过场景节拍预算。

### T-09 原子提交

在一个事务内：

1. 再次检查状态版本；
2. 追加权威事件；
3. 更新状态投影；
4. 递增战役状态版本；
5. 标记命令已经提交。

### T-10 叙述

叙述器只接收已提交结果、玩家可感知信息和文风设置。不得传入玩家不应知道的秘密。

### T-11 返回

标准响应至少包含：

```json
{
  "turnId": "turn_1001",
  "status": "completed",
  "stateVersion": 19,
  "narrative": "……",
  "visibleChanges": [],
  "availablePrompts": []
}
```

`availablePrompts` 只是示例选项，玩家始终可以自由输入。

## 4. 对过去事件的声称

玩家说“我前天送过他一瓶酒”时：

1. 记录玩家说出了这句话；
2. 查询是否存在匹配的历史事件；
3. 存在时，将历史事件作为当前交互证据；
4. 不存在时，不创建补写事件；
5. 根据语境将其视为记错、撒谎、玩笑或需要澄清的陈述；
6. NPC 的相信与否写入角色信念，不改变世界历史。

## 5. 重试和恢复

- 相同幂等键重复提交：返回原回合结果。
- 解析失败：允许重新解析，不创建世界事件。
- 导演失败：使用规则提供的安全默认候选。
- 提交冲突：重新加载最新版本并重新验证，不直接覆盖。
- 叙述失败：使用同一组已提交事件重新生成叙述。
- 客户端断线：重新查询 `turn_id`，不能重新执行命令。

如果叙述服务持续不可用，后端必须根据事件类型返回简短的确定性结果说明，避免已提交回合对玩家完全不可见。

## 6. 开发者审计记录

每回合应保存：

- 原始输入和解析结果；
- 意图解析尝试，包括模型可见请求、原始结构化输出、模型标识和失败代码；
- 实体解析候选；
- 读取的关键事实和历史事件编号；
- 前置条件结果；
- 骰子与规则修正；
- 导演原始提议；
- 校验拒绝项；
- 最终事件；
- 叙述版本、模型和提示词版本。

`intent_attempts` 属于非权威审计记录，不参与世界状态投影。原始模型请求和输出只允许后端内部审计读取；普通玩家回合详情只能看到解析来源、状态、模型标识和失败代码。
